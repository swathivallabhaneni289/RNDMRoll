1. Migration 0006 (Phase 1's clean-up is 0003, Phase 2's is 0004, Phase 2.1's `account_visibility` is 0005; hand numbered; never `migrate create -seq`) adds `entries`, `entry_photos` and two small things to `spins`: the column `settled_at` and `unique (id, user_id)`. Nothing else, and nothing in `users`.
2. One entry per local date: `unique (user_id, local_date)` and `unique (spin_id)`. The entry's spin is the date's latest spin at post time (a bonus counts). Category id and written name come from that spin; the entry copies neither.
3. `entry_photos` holds one row per photo with its `storage_key` (folder and file name) and `source` ('camera' or 'library', stored and never shown); the `entries` table holds no photo column. No response carries a key; responses carry `photos` (each with a `url`) and `photo_url` (the cover's), built by the server from the keys and the storage public base.
4. Reaction is one of six names or null: a database check and a Go list. The same six, in the same order, as `lib/entry/reactions.ts` in plan 03-02.
5. A post runs inside one `InUserTx` (the state-row lock, then the work): re-read the zone and read `now` once; existing entry for the date whose photo keys, in order, are the SAME list as the request's returns it (`already`); `daySettled` is `ErrDaySettled`; the spin number the phone saw must equal the latest spin's `seq` (`ErrSpinChanged`); the date's `late_until` passed is `ErrClosed`; then insert the entry and its photos, call the posted-day helper, set the spin's result to `posted` with `settled_at = now`. Any failure rolls all of it back.
6. `MarkPosted` keeps its signature, its transaction and its Phase 2 tests. Its body moves into a helper that takes an open transaction (`markPostedIn`); both call it. The helper holds all the rules: late is `now >= closes_at`; a date past `late_until` is refused for source `post`; the week count; the bonus grant.
7. A skip sets the latest spin's result to `skipped` and `settled_at = now`. It writes no posted day, touches no goal week and grants nothing. It is refused when the day is settled, when the spin number differs, and when `late_until` has passed. A repeat skip returns the same answer (`already`).
8. Delete removes the entry row only. The `posted_days` row and the spin's result stay, so the day cannot be posted again. Edit changes title, stars, reaction, comment and photos (add, remove, reorder, one to ten left); never the date, category, late stamp or posted day; no time limit.
9. Delete is `POST /v1/entries/{id}/delete` (the app's client has no DELETE and gets none). A repeat create with the same ordered list of photo keys is the retry rule.
10. After a change that drops photos (an edit that removes or replaces some, or a delete), the handler asks the store to remove each old file after the commit, best effort: an error is logged and ignored. Nothing else ever deletes a file.
11. Today's states (Task 1c) use `spins.settled_at`: a post or skip made at or after the spin's `window_closes_at` (in the late window) keeps Today on `posted` or `skipped` for that spin until the next opening; one made earlier returns to Phase 2's `waiting` after midnight.
12. The test reset (`POST /v1/test/reset`) also deletes the caller's entries first and ALL the caller's posted days (any source), then spins and goal weeks, and sets `bonus_held` to 0. Photo files stay in storage.
13. Time: no `time.Now()` in new code. `now` comes from the per-account clock, once per call, after the lock.
14. Photos (revision 2026-10-10). An entry has one to ten photos, in order; position 0 is the cover. One row each in `entry_photos`: the storage key, its content type (set by the server from the key's extension), the size the phone declared (optional, informational, the server never looks at the file) and 'camera' or 'library'. A create sends the ordered NEW keys. An edit sends the whole ordered list it should end with: a kept photo is named by its `id`, a new one by its `photo_key` with its `photo_source`, and anything left out is removed. One upload ticket per photo, from the same route. A key can belong to one photo row only, must be in the caller's folder, and the limit of ten is enforced in Go and by the table (position 0 to 9, unique per entry). An entry never has fewer than one photo: the service refuses an edit that would leave none, and nothing else writes these rows.
15. Today's entry summary (coordinator decision, 2026-10-10). `Today.entry` is `{id, late, title, stars, reaction, photo_url, photo_count}` or null: `stars` is the stored integer 1 to 10, `reaction` a name or null, `photo_url` the cover's link (position 0) built exactly as the entry's links are, `photo_count` 1 to 10. It is null when the shown spin's day has no entry, including after a delete. Below the HTTP layer the summary carries the cover's KEY (`CoverKey`, never serialised); the HTTP layer turns it into `photo_url` just before it writes (`linkToday`, Task 3c), so every Today the server sends has a link and no key.
</binding_decisions>
