<threat_model>
| Threat | Result | Why |
|---|---|---|
| The same photo uploaded twice on a retry, or a double post | Mitigate | The picked file's uploaded key is remembered; a ref blocks a second tap; the server treats the same photo key as the same post. |
| A stale screen posts to the wrong day or category | Mitigate | The phone sends `for_date` and `spin_seq` from the spin it showed; the server refuses a mismatch; the screen shows the message and asks for Today again. |
| The phone works out the winner, the date or lateness | Mitigate | No `Math.random`, `Date` or clock in `lib/entry`, `components/entry`, `components/today` or the route (greps). Lateness comes only from the server's `late`. |
| A wrong or huge file is sent | Mitigate | Type and size are checked before any upload; the ticket and the storage also refuse. Quality 0.8, standard JPEG. The ceiling is 50 MiB, the same as profile photos, so a normal full-size library photo is not refused. |
| Unsaved work lost by a swipe or a tab press | Mitigate | One `beforeRemove` guard, the same sheet as Edit wheel. |
| Emoji leaking into screen furniture | Mitigate | The six characters live in one file; the scan allows only that file. |
| Launch breaks (Unmatched Route, Welcome flash) | Mitigate | One list in one launch file is edited (the routes that hide the bar); the new route is in the Home stack; one cold launch is recorded. |
| The photo key reaching the screen | Mitigate | The app holds a key only between the upload and the post, never shows it, and never stores it. |
</threat_model>
