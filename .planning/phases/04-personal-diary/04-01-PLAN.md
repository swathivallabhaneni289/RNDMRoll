<binding_decisions>
Final.
1. **The contract is `04-CONTEXT.md` (API contract section), exactly.** Routes, query names, field names, order, error fields. Nothing here re-declares it differently.
2. **Read only.** The diary code never writes and never takes the per-person state-row lock (`InUserTx`): it reads through the pool, one query per fact. A read that sees a day between two writes is acceptable.
3. **One row per date.** A date is either posted (one entry) or skipped (the date's latest spin has result `skipped` and the date has no `posted_days` row), never both, and a deleted entry leaves no row. So the paging key is the date alone: the cursor is the last returned `local_date`, and the next page is every row with `local_date` strictly before it. The order stated in the contract ("then spin number descending") therefore never has to break a tie.
4. **Skipped rows only without a category filter.** With `category_id` set, only entries are returned (the filter is by the entry's spin's `category_id`). A `category_id` that is not the caller's gives an empty page, never an error and never another person's data.
5. **Chips.** Categories of the caller that have at least one entry, in wheel order (`position`) for live ones, then removed ones (archived) ordered by name ignoring case. Name is the category row's current name (the last name for a removed one). Sent with every page.
6. **Numbers.**
   - `spins` is the number of days spun: `count(*)` of the caller's spins with `kind = 'daily'`.
   - `week_streak` is the run of consecutive weeks, ending with the current week when its `goal_weeks` row exists, else ending with last week, counted over the caller's `goal_weeks` rows. The current week start comes from the stored zone and the service clock (`spin.WeekStart(spin.LocalDate(now, loc))`). A missing or unloadable zone gives 0, never an error (the Profile page must always load).
   - `tastes` average is the mean of `stars` divided by 2, to one decimal, computed in Go from the sum and the count with integer arithmetic (`tenths = (10*sum + count) / (2*count)`, half rounds up), sent as a number with one decimal (`4.6`). `count` is the number of entries.
   - `recent` is the newest three entries (newest `local_date` first).
   - `friends` comes from a `FriendCounter` the service is given. Phase 4 passes the zero implementation; Phase 5 passes the real one. The Reader knows nothing about friends.
7. **The key never leaves.** The Reader returns the entry record with its key; the HTTP layer builds `photo_url` with `EntryPhotoStore.PublicURL` through Phase 3's `Entry` JSON builder. No `photo_url` or `PublicURL` below `internal/httpapi`.
8. **Validation, by hand, before any read.** `category_id` must parse as a UUID (else 400 `validation_failed`, field `category_id`, reason `invalid`); `cursor` must decode to a valid date (field `cursor`, `invalid`); `limit` must be an integer from 1 to 50 (field `limit`, `invalid`), default 20. Both routes call `u.OnboardingComplete()` first (else 403 `profile_incomplete`), take the user only from the token, and are limited to 60 a minute with `KeyBySubject`.
9. **No migration** unless the query-plan check of Task 2 shows a sequential scan on `entries` or `spins` for one person's rows that an index would remove. Then exactly one reversible migration `0007` (hand numbered, `ls migrations` first: 0005 is Phase 2.1's and 0006 is Phase 3's) with its own migration test; otherwise `ls migrations` still shows 0001 to 0006 (twelve files).
10. **Time.** No `time.Now()` in new code. `now` comes from `clock.Clock.NowFor(userID)`, once per summary call.
11. **No `users` change**, no `ApiUser` change, no change to `/v1/me`. The new route is `/v1/me/summary` beside it. Phase 2.1's `account_visibility` (a column of `users` and a field of the user JSON) is neither read nor returned here: the summary does not need it.
</binding_decisions>

- **Rows.** Entries: `entries e join spins s on s.id = e.spin_id and s.user_id = e.user_id left join posted_days pd on pd.user_id = e.user_id and pd.local_date = e.local_date`, where `e.user_id = $1`, `($before is null or e.local_date < $before)` and `($category is null or s.category_id = $category)`; selecting the entry columns (including `photo_key`, never a link), `s.category_id`, `s.category_name` and `coalesce(pd.late, false)`. - **Tastes.** `select c.id, c.name, c.archived_at is not null, c.position, sum(e.stars), count(*) from entries e join spins s ... join wheel_categories c on c.id = s.category_id and c.user_id = s.user_id where e.user_id = $1 group by c.id, c.name, c.archived_at, c.position`, ordered like the chips.
