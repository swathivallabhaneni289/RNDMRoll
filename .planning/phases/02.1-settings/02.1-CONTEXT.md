## Implementation Decisions (defaults taken 2026-10-10, no questions asked)

### The developer's words
- **D-01 A Settings section like Instagram's.** Change the username, change the password, edit the bio on the profile page. "Whatever they posted" is read as: people can still change and delete their posts. That already exists on paper in Phase 3 (the entry page has Edit and Delete), so Settings links nothing new for posts. This is said once in the UI spec so the developer can object.
- **D-02 Public or private is the person's choice, DEFAULT PUBLIC for everyone,** switchable at any time ("totally up to the user"). Their later words win over the older Phase 6 notes (see "For the lead to forward").

### Where things live
- **D-03 Settings is a pushed page in the Profile stack,** not a tab (`app/(app)/profile/settings.tsx`; Username and Password are two more pages beside it). The bottom bar stays on all three, as on Edit wheel.
- **D-04 The gear** is a small component (`SettingsGear`) at the top right of the Profile page. On the CURRENT Profile page (Phase 1's "Make it yours." form in edit mode, which is the Profile tab after Phase 2) it sits at the right end of the header row. The Phase 4 Profile page mounts the same component. No new tab, no change to the bar.
- **D-05 Rows, in this order:** Edit profile, Username, Password, Private account, Log out. Edit profile opens Phase 1's existing form page (photo, name, username, bio, its username check) unchanged. Log out opens the same sheet text Phase 1 has ('Log out of RNDMRoll? You'll need to sign back in.', 'Log out', 'Stay logged in'); Phase 1's own Log out button on the form page stays too. **Superseded by D-16 for the row list** (the rows are now Notifications, Blocked accounts, Private account, Password, Log out); the Log out sheet and its words are unchanged.
- **D-16 Where things live (revision of 2026-10-13).** The developer's words (voice, cleaned): "the bio and username should be on the profile page, not in the settings ... in the settings we will have notifications, block people and account privacy." So:
  - **Profile page:** photo, the name beside it, the @username, the bio under it edited in place (`BioInline`), the three figures, tastes and recent activity, and ONE outlined button that says only 'Edit'. The Settings gear stays on this page.
  - **Edit page** (the Edit button opens Phase 1's form as a pushed page): photo with a visible 'Edit your picture' text under it that opens the same camera or library choices, name, username (with the live "taken or free" check, and the green 'Looks good.' for a free name), bio. 'Save changes' only (grey until something changes); a save goes back to the Profile page with 'Saved.'.
  - **Settings rows, in this order:** Notifications, Blocked accounts, Private account (the existing switch; the only privacy control; public is the default), Password (the existing change-password page), Log out (red, the existing sheet). Settings has NO Bio block, NO 'Edit profile' row and NO 'Username' row, and the Username page (its route, its screen and its check hook) is removed. D-06 (the Username page) and D-13 (the bio on Settings) are superseded; the server's `PATCH /me {username}`, its rules and its 409 are unchanged, and the Edit page uses them.
  - **Notifications page:** three switches, all ON by default, in plain words: 'Reactions and likes', 'Comments', 'Milestones and bonus spins'. Each saves on its own toggle, with an inline error and a revert on failure.
  - **Blocked accounts page:** the people the person blocked (round photo, name, @username, an 'Unblock' text link), and 'You haven't blocked anyone.' when there are none. Blocking comes with the person pages of Phases 5 and 6.
  - **Server contract** (built by another plan after Phase 3's server; it may answer 404 until then, and the app then shows the three switches ON and an empty list, never an error screen): `GET /v1/me/notification-settings` answers `{reactions, comments, milestones}` (booleans); `PATCH /v1/me/notification-settings` takes any of the three and answers the same body; `GET /v1/me/blocks` answers `{items: [{user: {id, name, username, photo_url}, blocked_at}]}`; `DELETE /v1/me/blocks/{user_id}` answers 204. The app's calls are in `lib/api/account.ts`; its client gained a `delete` method for the last one (the first and only DELETE the app sends).

### Username
- **D-06 (the separate Username page is superseded by D-16; the Edit page's username box keeps the rules below) Change username uses the existing `PATCH /me`** (field `username`), the existing rules (3 to 20 of a to z, 0 to 9 and underscore; always lower case; unique), the existing live check (`GET /usernames/available`, 400ms debounce) and the existing 409 `username_taken` with three alternates. No password is asked (default; Instagram does not either). The old name is free to others at once. The only new server thing is a general limit on `PATCH /me` of 30 a minute per caller. A username can also be used to log in, so the page says so in one line.

### Password
- **D-07 Change password is a new route, `POST /v1/me/password`,** body `{current_password, new_password}`. It checks the current password (bcrypt), applies Phase 1's one password rule (8 to 72, counted in bytes by bcrypt), refuses a new password equal to the old one, stores the new hash, and in ONE transaction replaces every refresh token of the account with one new token. It answers with the same body as log in (`access_token`, `refresh_token`, `expires_in`, `user`), so this phone keeps its session by saving the new tokens; every other phone is signed out the next time its short access token (15 minutes) needs a refresh. A wrong current password is `400 validation_failed` with `field: "current_password"`, never a 401 (a 401 on a signed-in call means "your session is gone"). Limited to 5 a minute per caller and 20 a minute per address. One new-password box, no "type it again" box, like sign-up.
- **D-08 The app keeps the session without touching `lib/session/store.ts`:** the new tokens go through the existing `signIn(result)` of the session context, which saves both tokens and the user and leaves the status signed in.

### Public or private
- **D-09 Storage:** `users.account_visibility text not null default 'public' check (in 'public','private')`, migration `0005_account_visibility` (Phase 2's is 0004). Every existing row, the four real dev accounts included, becomes 'public' by the column default and is never edited by hand. The value is part of the user JSON the app already reads (`GET /me`, sign-up, log in, `PATCH /me`).
- **D-10 Setting it:** a field `account_visibility` on `PATCH /me` (the existing partial-update route; any value but 'public' or 'private' is `400 validation_failed` field `account_visibility`). The Settings switch saves on toggle, with no confirmation (it is reversible), refreshes the session user, shows an inline error and puts the switch back on failure.
- **D-11 Under 18 (a recommendation the developer can drop):** an account whose birthday makes it under 18 on the day it is created STARTS 'private'. It is the same switch for them; they can turn it off. The whole rule is one function, `user.DefaultVisibility(age)` in `internal/user/visibility.go`, called from the sign-up path; drop the rule by making it return 'public'.
- **D-12 What the setting does (paper for Phase 5 and 6):** in this phase NOTHING reads it except the Settings page. Phase 5 (Friends view) shows a friend's posts to accepted friends whatever their setting. Phase 6 (Global) shows a post to everyone only when the AUTHOR's `users.account_visibility` is 'public' at the time the list is read; there is no per-post copy of the setting, so switching to private hides past posts from Global at once and switching to public shows them. Those phases must read the author's column (or the `account_visibility` field of the user JSON), nothing else.

### Bio
- **D-13 `BioInline`** is a self-contained component (one optional prop, `label`, which draws the small-caps 'Bio' label above the text; the Phase 4 page leaves it off). It reads `user.bio` from the session, shows it as Body text ('Add a bio' in `muted` when empty), and a tap turns it into an editor in place: multiline, the Phase 1 limit of 160 characters, a live count, 'Save' and 'Cancel' text links. Save sends `PATCH /me {bio}` and refreshes the session user. It works anywhere inside the signed-in app. It was mounted on the Settings page first; since D-16 Settings does not mount it, and it is mounted on the Profile page (under the @username). The CURRENT Profile page already has an editable Bio box in its form (Phase 1, `ProfileForm.tsx`, saved by 'Save changes'); that box is left alone.

### Housekeeping
- **D-14 Numbering:** this phase is the decimal phase 2.1 (a marked insertion); its plans are 02.1-01 and 02.1-02. Migration 0005 is this phase's, so Phase 3's migration becomes 0006 and the later phases shift by one.
- **D-15 No new native module, no new package.** The switch is React Native's own `Switch`. Never run `expo lint`. Tokens only. Local commits, explicit paths, never pushed. The four real accounts are never touched.

### Claude's Discretion (safe defaults, told to the developer, no question asked)
- The notice after a change ('Username changed.', 'Password changed. Other phones are signed out.', 'Saved.') shows for 3 seconds on Settings, under the title, as a polite live region (the same idea as Phase 2's 'Saved.' on Profile). It travels through a tiny in-memory store, not through route parameters.
- Show and Hide on the password boxes follow Phase 1's sign-up pattern (a small text link on the label row).
- The Username page never asks the server whether the person's OWN current name is free: back at the stored value it shows nothing and Save stays grey (Phase 1's form does the same).
- Another phone's old access token keeps working for at most 15 minutes after a password change (it is a signed token, not a lookup). The refresh tokens are the real sessions and they are gone at once.
- A person under 18 who turns the switch to public is allowed (the developer said "totally up to the user"). A line on the Settings page is not added for them; the server could refuse later if the developer asks.

### For the lead to forward (the other window writes Phases 4 to 6)
The Phase 6 notes say "Private by default", "under 18 is always Private" with the switch disabled, and put the switch on the Edit profile page ("Public account", default off). The developer's later words win: DEFAULT PUBLIC for everyone, the switch is "Private account" (ON means private) in SETTINGS, and under-18 accounts only START private and can switch like anyone else. Also: the Phase 4 Profile page should mount `SettingsGear` at its top right and `BioInline` under the @username (`SettingsGear` takes no props, `BioInline` one optional one); this phase writes both; the page's bio is not drawn in the developer's picture 12, so this is an addition they asked for in words.

## Existing Code Insights

### What Phase 1 already does (found by reading the code, 2026-10-10)
- **The username and the bio are ALREADY editable on the Profile page.** `components/profile/ProfileForm.tsx` in `edit` mode (the Profile tab) has the Username box (with the live check, alternates and green 'Looks good.') and the Bio box (multiline, 160, count), both saved by 'Save changes' through `PATCH /me`. What is missing is a Settings page, a password change, a way to edit the bio on a page that SHOWS the bio, and the public or private choice.
- **There is no password change anywhere.** `user.Repository` has no method that writes `password_hash` after sign-up; the server has sign-up, log in, refresh and log out only.
- **Sessions are refresh tokens** (`refresh_tokens`, SHA-256 hashed, 30 days, rotated on every refresh) plus a 15 minute signed access token. `RefreshService.RevokeAll` and `RefreshTokenRepository.RevokeAllForUser` exist; "replace all with one new" does not.
- **`PATCH /me` has no rate limit** and refuses a birthday by name. `GET /usernames/available` is public and limited to 90 a minute per address.
- **The password rule** is one function, `passwordReason` (8 to 72 characters, bcrypt's 72 BYTES checked again at hashing).
- **The session context's `signIn(result)`** saves both tokens and the user, clears `extrasPending`, and keeps the status authenticated.

### Reusable assets
- `TextField` variant `soft` (label, prefix, `status`, `error`, `success`, `hint`, `showCount`, `multiline`), `PrimaryButton`, `TextButton`, `AppText`, `Screen`, the Show and Hide link on the password label row, the alternates chips, Phase 2's `ConfirmSheet` (the Log out sheet's words go into it).

### Integration points
- **Routes:** `POST /me/password` goes on the signed-in group in `NewServer` (`RequireAuth`, then `RequireUser`), in a new `AccountHandler`, nil-safe so existing test builders that do not set it still work.
- **Migration:** 0005 adds one column and one check; `integrationRunMigrations` in the httpapi tests and the helpers in `postgres_test.go` read the files, so they need no pin change.
- **App routes:** three new files in `app/(app)/profile/` and three `Stack.Screen` lines in that folder's `_layout.tsx`. No launch file is edited (`app/index.tsx`, `app/_layout.tsx`, `app/(auth)/_layout.tsx`, `app/(app)/_layout.tsx`, `lib/session/store.ts`, `lib/api/client.ts`).
- **One edit to a Phase 1 file:** `components/profile/ProfileForm.tsx` gets the gear in its header row (edit mode in the tab only). Phase 4 gives this file one more optional prop (`pushed`); the two edits do not overlap.
- **Test traps:** the migration tests restore the latest version in a cleanup; a user-repository fake exists in three test files, so the visibility field is added to the shared structs, not to the interface, and the new `PasswordChanger` interface is implemented only by the Postgres repo and the httpapi fake.
