# Phase 2.1 - UI Design Contract (Settings)

> Design contract plan 02.1-02 builds from. PHASE 2.1. It inherits every token, type size, spacing step, radius and elevation tier from `01-foundation-accounts/01-UI-SPEC.md` (revision 18 or later) and the text roles, bar and Profile-tab rules of `02-daily-roll/02-UI-SPEC.md` (revision 6). No new colour, font, size or radius is added (section 2). The developer drew no Settings picture, so the look follows their Profile picture (screen 12) and their Notifications picture (screen 11): a serif title under a back arrow, plain rows between hairlines, nothing round, no cards. There is no imagery in this phase except the gear and the row chevrons (Ionicons), and the small round photos of the Blocked accounts list (the existing avatar).
>
> **Revision 2 (2026-10-13, decision D-16 of `02.1-CONTEXT.md`).** The developer: "the bio and username should be on the profile page, not in the settings ... in the settings we will have notifications, block people and account privacy." Settings no longer shows the bio and has no Edit profile and no Username row; the Username page is gone. Settings rows are now Notifications, Blocked accounts, Private account, Password and Log out, and two pages are new (sections 8b and 8c). Where an older paragraph below disagrees, this note and the sections marked "(D-16)" win.

## 2. Tokens added (the only new design values)

None. Page titles use Phase 2's `title` role (`Domine_400Regular` 32/38). Everything else is an existing token:

| Need | Token |
|---|---|
| Page, rows | `dominant` fill, `ink` Body text |
| Values on a row, helper lines, small-caps labels | `muted` (5.82:1) |
| Hairlines | `divider` |
| Pressed row | `secondary` fill |
| Log out text, error lines | `destructive` |
| Radius on every tappable | `md` (8dp) or less; nothing round is drawn by this phase |

The switch is React Native's own `Switch` (a system control, so no new native module): track `ink` when on, `divider` when off, thumb `dominant`. It is the one control whose shape the system draws; it is not styled with a radius token and the radius scans do not see it.

- **Profile page** (the page of the developer's picture 12, built as Phase 4's Profile part): it has no header row, so a 44dp row is added above its photo row with the gear right aligned (the notice 'Saved.' shows at the left of the same row for 3 seconds after the Edit page saves).

The Profile route no longer shows that form, so that line stays in the file untouched and is not reached; never on the first-run page and never on sign-up.

3. **Notice line**, `sm` below: a Label in `muted`, one line, polite live region. Its 20dp is always reserved so nothing jumps. It shows 'Password changed. (D-16: 'Username changed.' and 'Saved.' are no longer sent to this page; 'Saved.' goes to the Profile page.)
4. **Rows**, `lg` below. A 1dp `divider` hairline above the first row and one under each row. Each row is at least 56dp high, full width, Body role, `ink`, with a trailing area: a value in Body `muted` (one line, cut with an ellipsis) and Ionicons `chevron-forward` 20dp `muted`, `xs` apart. Pressed: `secondary` fill, no radius. In this order (D-16):
   - **Notifications** opens `/(app)/profile/notification-settings` (section 8b). No value.
   - **Blocked accounts** opens `/(app)/profile/blocked-accounts` (section 8c). No value.
   - **Private account**: the switch row (section 8). No chevron.
   - **Password** opens `/(app)/profile/password`. No value.
   - **Log out**: 'Log out' in `destructive`, no chevron, opens the Log out sheet (`LogOutSheet`).
5. `xl` of space at the end.

**Not on this page (D-16).** There is no Bio block, no 'Edit profile' row and no 'Username' row. The bio is edited in place on the Profile page; the photo, name, username and bio are edited on the Edit page the Profile page's 'Edit' button opens.

**Log out sheet.** Phase 2's `ConfirmSheet` (the same modal, scrim, top corners and padding as Phase 1's Log out sheet, already on the `radius.lg` list): the title 'Log out of RNDMRoll?' (Heading role), the Body "You'll need to sign back in.", then two full-width rows of at least 56dp with a hairline between: 'Log out' (in `destructive` when the built `ConfirmSheet` has the per-row destructive flag, which Phase 3 adds; otherwise plain `ink`) and 'Stay logged in'. Phase 1's own Log out on the form page is not touched.

**Posts.** There is no row for posts. A person edits or deletes a post from its entry page (Phase 3: the Edit and Delete footer), which the Phase 4 Diary and Profile page open. This is said here once so the developer can object.

## 5. The Username page (REMOVED by D-16)

Settings has no Username row any more and this page, its route (`profile/username`), its screen and its check hook are gone. The username is changed in the username box of the Edit page (Phase 4's UI spec section 4.6), which keeps the live check and shows the green 'Looks good.' for a free name. The text below is kept only as the record of the rules the Edit page's box follows.

(Record of the removed page.) Pushed from the Username row, bar showing. `Screen` as in section 4. Top to bottom:
1. Back row (as 4.1).
2. `md` below: title 'Username' (`title` role).
3. `lg` below: `TextField` variant `soft`, label 'Username', prefix '@', the current username as the starting value, `autoCapitalize="none"`, `autoCorrect={false}`, `status` from the live check. The value is lower-cased as typed.
4. If the name is taken: `xs` below, the alternates as small chips exactly as Phase 1's form draws them (`elevation.subtle`, `radius.sm`, Label); a tap puts the alternate in the box.
5. `md` below: the Label 'This is how people find you and how you log in.' in `muted`.
6. If a save failed, `md` below: one Body line in `destructive` (section 9).
7. `lg` below: `PrimaryButton` 'Save username' (no arrow): grey (the existing disabled look) until the box holds a value that is different from the stored one, matches `^[a-z0-9_]{3,20}$` and the live check says it is free. While saving it shows its spinner.

**Live check.** Phase 1's rules, unchanged: nothing is checked while the box holds the stored username or is empty (the person's own name is never "taken" against itself); a value that is not 3 to 20 of a to z, 0 to 9 and underscore shows '3 to 20 letters, numbers, or underscores.' at once; otherwise a 400ms debounce, then `GET /usernames/available`; free shows the green 'Looks good.' (the `success` note); taken shows "That username's taken. Try one of these:" with the alternates (or "That username's taken." with none); a failed check shows "Couldn't check that username. Try again."

**Save.** `PATCH /me {username}`. Success: refresh the session user, leave the notice 'Username changed.' for Settings, go back. A 409 `username_taken` (a race) shows the taken message and its `suggestions`.

## 6. The Password page

Pushed from the Password row, bar showing. Top to bottom:
1. Back row.
2. `md` below: title 'Password'.
3. `lg` below: `TextField` soft, label 'Current password', `secureTextEntry` (off while Show is on), `autoComplete="current-password"`, `textContentType="password"`, with the Show or Hide link on the label row (Phase 1's pattern: an absolutely placed Label link, label 'Show password' or 'Hide password').
4. `md` below: `TextField` soft, label 'New password', `autoComplete="new-password"`, `textContentType="newPassword"`, its own Show or Hide link. Under it, until it is judged: the Label 'At least 8 characters.' in `muted`. On blur: too short shows 'Password must be at least 8 characters.'; over 72 bytes shows 'That password is too long. Use 72 characters or fewer.'; the same text as the current box shows 'Choose a password that is different from your current one.'; a good one shows the green 'Looks good.'. One new-password box only, like sign-up (there is no "type it again").
5. If a save failed, `md` below: one Body line in `destructive` (section 9).
6. `lg` below: `PrimaryButton` 'Save password' (no arrow): grey until the current box is not empty and the new one is good and different. Spinner while saving.

Nothing is saved on the phone except the new tokens the server returns.

**Save.** `POST /me/password {current_password, new_password}`. Success (200, a log-in shaped body): `signIn(result)` of the session context stores the new tokens and user (this phone stays signed in), the boxes are cleared, the notice 'Password changed. Other phones are signed out.' is left for Settings, go back. Failure: a `validation_failed` with `field: "current_password"` shows 'That is not your current password.' under the Current box and keeps the typed new password; any other `validation_failed` shows 'That password can't be used. Try a different one.' under the New box; 429 shows 'Too many tries. Wait a minute and try again.'; no connection shows 'Couldn't connect. Check your connection and try again.'; anything else 'Something went wrong. Please try again.'. A failed save never clears the boxes.

## 7. Bio in place (`BioInline`)

Since D-16 the only place that mounts it is the Profile page, which leaves the label off and mounts the component under the photo row (the @username is in that row); Settings does not show the bio. It reads `user.bio` from the session.

| State | What shows |
|---|---|
| Reading, has a bio | the bio in Body role, `ink`, left aligned, line breaks kept; under it, `xs`, the text link 'Edit bio' (Label, `ink`, underlined, 44dp hit area). The bio text is also a tap target. |
| Reading, no bio | the text link 'Add a bio' (Label, `muted`, underlined, 44dp hit area). |
| Editing | `TextField` soft, label 'Bio', hint 'Optional', multiline, 3 lines, `maxLength` 160, the count inside the box, placeholder "Tell people what you're spinning for.", focused on open. Under it, `sm` below, one row: 'Save' (`TextButton`, disabled until the text differs from the stored bio) and 'Cancel' (`TextButton`, tone `muted`), `lg` apart. A failed save shows one Label in `destructive` under the row. |
| Saving | the box is not editable and 'Save' is disabled; no spinner, no layout change. |

**Save.** `PATCH /me {bio}` with the trimmed text (an empty text clears the bio). Success: refresh the session user and go back to Reading with the new text; there is no notice. 'Cancel' drops the edit. Leaving the page while editing drops the edit (it is short and visible). The 160 limit and the control-character rule are the server's (Phase 1); the box stops typing at 160.

The current Profile page's own Bio box (in Phase 1's form, saved by 'Save changes') is left as it is.

## 8. The Private account row

A row of section 4, `Screen`-wide, at least 56dp: the label 'Private account' (Body, `ink`) at the left and the `Switch` at the right. Under the row, `xs` below inside the same hairline block, the Label in `muted`: 'Public accounts can appear on Global. Private accounts are seen by friends only.' The switch is ON when `user.account_visibility` is 'private' and OFF when it is 'public' (the default for everyone).

**Behaviour.** The whole row is one switch element: a tap anywhere on it toggles (the system switch inside it ignores touches itself). The change shows at once, the row is disabled while the save runs (`PATCH /me {account_visibility}`), and on success the session user is refreshed. On failure the switch goes back to what it was and one Label in `destructive` shows under the sentence ('Couldn't connect. Check your connection and try again.' for no connection, otherwise 'Something went wrong. Please try again.'); it clears on the next try. There is NO confirmation dialog: the choice is reversible.

**What it does.** In this phase it is only stored and shown (CONTEXT D-12). Nothing on screen changes when it is flipped, other than the switch. It is the only privacy control in the app (D-16); public is the default.

## 8b. The Notifications page (D-16)

Pushed from the Notifications row, bar showing. `Screen` as in section 4. Top to bottom: the Back row (as 4.1); `md` below, the title 'Notifications' (`title` role, a header element); `lg` below, a 1dp `divider` hairline and then three switch rows, each at least 56dp high with a hairline under it, built like the Private account row (the label in Body `ink` at the left, the system `Switch` at the right, the whole row one switch element):

| Row | What it covers |
|---|---|
| Reactions and likes | reactions and likes on the person's posts |
| Comments | comments on the person's posts |
| Milestones and bonus spins | the weekly goal and bonus spins |

All three are ON until the person switches one off.

**Behaviour.** Each switch saves on its own toggle: `PATCH /me/notification-settings` with that one boolean. The change shows at once and the row is disabled while its save runs. On success the switch follows the server's body. On failure it goes back to what it was and one Label in `destructive` shows under that row ('Couldn't connect. Check your connection and try again.' for no connection, otherwise 'Something went wrong. Please try again.'); it clears on the next try. There is no confirmation and no 'Save' button. The page asks `GET /me/notification-settings` once when it opens; a late answer never overwrites a switch the person has already touched.

**Server not live yet.** The routes are built by another plan after Phase 3's server. Until then `GET` answers 404 (or the phone has no connection): the three switches simply show ON and the page draws no error. A toggle then fails with the red line and the switch goes back, which is the specified failure behaviour. Nothing on screen sends or receives a notification in this phase; the setting is only stored and shown.

## 8c. The Blocked accounts page (D-16)

Pushed from the Blocked accounts row, bar showing. `Screen` as in section 4. Top to bottom: the Back row; `md` below, the title 'Blocked accounts' (`title` role, a header element); `lg` below, either the list or the empty sentence.

- **List.** A 1dp `divider` hairline above the first row and one under each row. A row: a round photo 44dp (the existing `DialAvatar`, drawn at that size by `SizedAvatar`; the person's initials when they have no photo), `md`, a column with the name (Body, `ink`, one line, cut with an ellipsis) and, under it, the '@username' (Label, `muted`, one line), and at the right the text link 'Unblock' (Label, `ink`, underlined, 44dp hit area). A person with no name shows the @username alone. The photo is decoration; the row is spoken as 'name, @username' and the link as 'Unblock {name}'.
- **Unblock.** `DELETE /me/blocks/{user_id}` answers 204. The row leaves the list at once on success. While the call runs the link is `muted` and disabled. On failure the row stays and one Label in `destructive` shows under it (the same two sentences as the switches).
- **Empty.** The Body sentence "You haven't blocked anyone." in `muted`, a polite live region. It is not drawn until the first answer settles, so it never flashes before a list.
- **Server not live yet.** `GET /me/blocks` answers `{items: [{user: {id, name, username, photo_url}, blocked_at}]}`. Until the route exists it answers 404 (or there is no connection): the page shows the empty sentence and no error. There is no way to add a person here; blocking comes with the person pages of Phases 5 and 6.

## 11. Accessibility

- **Gear.** A button, label 'Settings', hint 'Opens your settings.', 44dp hit area.
- **Settings page.** The title is a header element. Each row is one button, read by its label; hint 'Opens the page.' for the page rows (Notifications, Blocked accounts, Password). 'Log out' is a button with the hint 'Asks first.' The back control is a button labelled 'Back'.
- **Notice line.** A polite live region, so VoiceOver reads it once when it appears.
- **Private account.** One element with `accessibilityRole="switch"`, label 'Private account', state checked or not, hint 'Public accounts can appear on Global. Private accounts are seen by friends only.' A failure message is a polite live region.
- **Notifications page (D-16).** The title is a header element. Each row is one element with `accessibilityRole="switch"`, its label ('Reactions and likes', 'Comments', 'Milestones and bonus spins'), state checked or not, disabled while it saves. A failure message is a polite live region.
- **Blocked accounts page (D-16).** The title is a header element. A row's name and @username are one element, 'name, @username'; the photo is hidden from VoiceOver; 'Unblock' is a button labelled 'Unblock {name}'. The empty sentence is a polite live region.
- **Password page.** Fields are labelled by their small-caps labels; the count and the 'Looks good.' note are read as Phase 1 reads them; the Show and Hide links are buttons 'Show password' and 'Hide password' for their own field (`accessibilityLabel` includes 'current' or 'new').
- **Bio (on the Profile page).** Reading is a button: 'Bio: {text}. Edit your bio.' (no bio: 'Add a bio'). Editing: the field is labelled 'Bio', its count is read ('12 of 160 characters'); 'Save' and 'Cancel' are buttons.
- **Targets.** Every tappable is at least 44dp (rows 56, gear 44, links 44).
- **Text size.** Everything scales with the phone's text size.
- **Contrast.** `muted` on `dominant` 5.82:1, `ink` 17.32:1, `destructive` as in Phase 1, the green 'Looks good.' as in Phase 1.

## 12. Notes for the plan

- **Plan split.** 02.1-01 is the server (the visibility column and field, the change-password route, tests, cutover). 02.1-02 is the app (API calls, pure rules, the components of sections 3 to 8, three routes, the gear, a short walkthrough). D-16 (2026-10-13) added two pages and their calls (`lib/api/account.ts`: the notification settings and the blocks; `components/settings/NotificationSettingsScreen.tsx` and `BlockedAccountsScreen.tsx`; routes `notification-settings` and `blocked-accounts`) and removed the Username page. The server routes they call (`/me/notification-settings`, `/me/blocks`) are built by another plan after Phase 3's server, so they may answer 404 for now (section 8b and 8c). The API client gained a `delete` method for `DELETE /me/blocks/{user_id}`, the only DELETE the app sends.
- **Wiring.** The pages read the session user (`useSession().user`) and refresh it with `reloadUser()` after a save. The new tokens of a password change go through `signIn(result)`; `lib/session/store.ts` is not edited. A tiny in-memory store (`lib/settings/notice.ts`) carries the notice from a page back to Settings: set just before `router.back()`, read by Settings on focus, cleared after 3 seconds.
- **Pure logic in pure files** (`lib/settings/rules.ts`: the username pattern, the password problems, the bio length, 'is it the same as before'), checked by a throwaway node script and by device steps.
- **Launch.** No launch file is edited. Three `Stack.Screen` lines go in `app/(app)/profile/_layout.tsx`; one cold launch is recorded after the routes exist.
- **One edit to a Phase 1 file:** `components/profile/ProfileForm.tsx` gets the gear in its header row. Phase 4 adds an optional `pushed` prop to the same file; the edits do not overlap. (Since D-16 the Profile route shows the new Profile page, so that gear line is not reached; the page mounts the gear itself.)
- **Never run `expo lint`.** No new native module (the switch is React Native's). Tokens only, no hex. No `radius.full` or `radius.lg` is added, so Phase 2's radius lists are unchanged.
