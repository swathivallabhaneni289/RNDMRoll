## The wire contract (for plan 02.1-02)

- User JSON, everywhere a user is returned: `account_visibility` is `"public"` or `"private"`.
- `PATCH /v1/me {"account_visibility": "public" | "private"}`: 200 with the user body. Any other value, of any JSON type, is `400 {"error":"validation_failed","field":"account_visibility","message":"This value is not valid."}` and nothing in the request is applied. 429 `rate_limited` after 30 a minute per caller.
- `POST /v1/me/password {"current_password", "new_password"}`:
  - 200 `{"access_token","refresh_token","expires_in","user"}`, the same shape as log in. The phone saves it through `signIn(result)`.
  - 400 `validation_failed` with `field` and a fixed `message` (the body carries no reason code, only the text):
    - `current_password`: "This field is required." or "That password is not right."
    - `new_password`: "This field is required.", "This value is too short.", "This value is too long." (73 characters, or over 72 bytes), or "Choose a different password."
  - 400 `validation_failed` with no field ("Request body is not valid."): unreadable body or a wrong JSON type.
  - 401 `token_invalid` or `token_expired` (no token, a deleted account); 413 `payload_too_large`; 429 `rate_limited` after 5 a minute per caller or 20 a minute per address.
- A wrong current password is never a 401.

## Differences from the plan (each is a choice the plan left open, or a narrowing)

1. **Task 3 steps 2 to 9 are not done** (binary backup, dump, rehearsal, `up 1` on dev, API restart, live check on dev, rollback note). The lead does the cutover; see "Left for the cutover".
2. **`ChangePassword` revokes twice, so it is four statements, not three** (update the hash; revoke all; insert the new token; revoke every active token except the new one). Reason: a refresh on another phone that is in flight at that moment (it holds the lock on its old token and has made its new one) makes the first revoke wait, and the token it then commits was not visible to that statement, so it would have stayed alive after the change. The second statement starts after the wait and ends it. `TestUserRepo_ChangePassword_RevokesARefreshThatCommitsWhileItRuns` holds such a refresh open and fails without the second statement (checked by removing it).
3. **A wrong JSON type for `account_visibility`** (a number, a boolean, an object) is made a field error by checking the decoder's `*json.UnmarshalTypeError` for that field in `patchMe`, so the request struct stays `AccountVisibility *string` as the plan says and the test list's "a number" gets field `account_visibility`. Other fields keep the generic 400 for a wrong type, as before.
4. **The two limits on `/me/password` run per caller first, then per address**, so one person's retries do not use up the address's 20 for everyone behind it.
5. **The access token is made before the transaction**, so it cannot fail after every session is gone.
6. **`ProfileHandler.currentUser` now delegates to a shared `callerAccount(c, users)`** in `profile.go`; the account handler uses the same lookup rather than a copy. Behaviour is unchanged.
7. **`IssueInTransaction` returns `ctx.Err()` at once** when the context is already done, and does not call `persist`.
8. **Test names and files:** the sign-up and switch tests are in `internal/httpapi/visibility_test.go`; the end-to-end test is in `internal/httpapi/account_integration_test.go`; the full test rig got two options (`account`, `logger`) and the integration rig always carries the account handler. Extra tests beyond the plan's list: a repository failure is the fixed 500 and changes nothing, the account gone mid-change is 401, an account with no stored hash is refused even for the dummy hash's own text, and the route is not mounted when `Deps.Account` is nil.
9. **Tag:** `pre-phase2.1` was made at `01f10ba`, when the tracked tree held other windows' uncommitted documents and app files (none in server paths).
