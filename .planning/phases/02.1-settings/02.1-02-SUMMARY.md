## Where it differs from the paper

1. **`app/(app)/profile/index.tsx` is edited (one file the plan did not list).** Settings is pushed over the Profile page, which stays mounted underneath, and `ProfileForm` copies name, username and bio into its own state when it mounts. Without a change, Back from Settings would show the OLD username or bio with "Save changes" enabled, and tapping it would send the old value back (walkthrough step 14 would fail). The route now adds a generation number to the form's key and bumps it when the page regains focus AND the four fields the form copies (name, username, bio, avatar) differ from what they were when the page lost focus. Nothing is remounted while the page stays focused, so the form's own "Saved." note and an unfinished edit are kept. `ProfileForm.tsx` still gets only the gear.
2. **The gear sits in a wrapper with `marginLeft: space.sm` and `marginVertical: -15`.** A 44dp gear in the header row would otherwise make the row about 30dp taller and push "Make it yours." down. The overhang keeps the row's height; the 44dp touch area is the gear's own frame. The diff of `ProfileForm.tsx` against the commit before Task 3 is the import, this wrapper and its two comment lines (+8).
3. **`git diff pre-phase2.1 -- components/profile/ProfileForm.tsx` is not "only the gear"** (47 insertions), because the tag predates Phase 2's `inTab` commit. Against the commit before Task 3 it is only the gear.
4. **`useUsernameCheck` also returns `markTaken(suggestions)`** (the plan lists seven fields). The 409 `username_taken` at save time needs a way to show the same taken state with the fresh alternates; the hook is the one place that owns that state.
5. **The username page shows the green "Looks good." (the box's success note), not the box's own "Available".** The hook's `available` is passed to `TextField` as `status="idle"` plus `success`. The spec and walkthrough step 6 say "Looks good."; the profile form itself still shows "Available" (not touched).
6. **`scripts/check-settings.ts` is not in the repo.** `scripts/` was not on the lead's list of paths. The script is at `/private/tmp/claude-501/-Users-swathivallabhaneni-code-RNDMRoll/440000ec-3418-440b-9f7f-1d145994195d/scratchpad/check-settings.ts`; it imports the repo files by absolute path built from the current directory, so it runs from anywhere with `node --experimental-strip-types <path>` started in the repo root. To keep it as the paper says: copy it to `scripts/check-settings.ts` (it needs no edit).
7. **Small additions inside the plan's components:** `SettingsRow` has an optional `accessibilityLabel` (so the Username row is spoken "Username, {name}" as section 11 says); `SettingsScreen` also calls `AccessibilityInfo.announceForAccessibility` for the notice (iOS does not read a live region by itself); `BackRow`, `UsernameScreen` and `PasswordScreen` go to the Profile page when there is nothing to go back to; `BioInline` draws its small-caps label only while Reading (the Bio box draws the same label itself while Editing); Cancel is disabled while a bio save runs; passwords are counted in characters (code points) as the server does, and bytes for the 72 limit.
8. **'Log out' in the sheet is plain ink**, as the plan allows: the built `ConfirmSheet` has no per-row destructive flag. The red Log out is the Settings row.
9. **No cold launch was done** (Task 3 step e). See "What happened to the simulator" below; the screenshots show the app before and after Metro reloaded it, nothing was terminated or launched by this plan.
10. **The notice 'Saved.' of section 4 has no sender yet.** Only 'Username changed.' and 'Password changed. Other phones are signed out.' are set (the plan's wiring). The bio save has no notice by design.

## What happened to the simulator (needs the lead's eyes)

The simulator was on Today, signed in, when Task 3 started (screenshot at 14:05). Task 3 added three route files under `app/`, which makes Metro reload the whole app. At 14:06:10 the API log shows, within 60ms:

```
POST /v1/auth/refresh 200
POST /v1/auth/refresh 401
GET  /v1/me           200
POST /v1/auth/logout  204
```

and the next screenshot (14:07) is the Welcome page: **the phone signed itself out, and the developer must log in again.** This is a race in `lib/session/store.ts` that exists without this plan: two refreshes of the same refresh token start close together after a reload (the restore on mount and the client's 401 path both call the refresh handler), the second gets 401 because the first rotated the token, and `doRefreshSession` treats that 401 as definitive when the first has not yet written the new tokens (`stillStored` is still true), so it signs out and deletes the keychain tokens. The rule for this task is to report and not edit the store. A fix, if wanted, is small: make `doRefreshSession` single-flight (one shared in-flight promise for the restore and the client path), and in its catch do not sign out when another refresh succeeded meanwhile. It can also bite a real cold launch with an expired access token and a screen that fires a request at once, so it deserves its own small plan. It was not caused by any line of this plan; this plan's writes only triggered the reload.
