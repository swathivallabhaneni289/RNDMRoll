<binding_decisions>
Final.
1. `02.1-UI-SPEC.md` is the design. Every string comes from its section 10. This plan adds none.
2. **The session stays untouched.** A password change returns a log-in shaped body; the screen passes it to `signIn(result)` from `useSession()`, which saves both tokens and the user and keeps the status authenticated. `lib/session/store.ts` and `lib/api/client.ts` are not edited (the new errors are field errors and the existing codes).
3. **Reading the user.** Every component reads `useSession().user` and refreshes it with `reloadUser()` after a save. Nothing keeps a second copy of the profile.
4. **The username check is a hook** (`lib/settings/useUsernameCheck.ts`) that repeats `ProfileForm.tsx`'s rules (pattern, 400ms debounce, never "taken" against the stored value, alternates, a stale answer is ignored). `ProfileForm.tsx` is NOT refactored to use it (three plans touch that file; unify later).
5. **Pure rules in a pure file** (`lib/settings/rules.ts`, no React, no app imports). Its constants repeat the server's (`USERNAME_PATTERN`, 8 characters, 72 bytes, 160 for a bio) with a comment naming their other homes.
6. **The notice** that Settings shows after Username or Password is a module store (`lib/settings/notice.ts`, `useSyncExternalStore`): a page calls `setSettingsNotice(text)` just before `router.back()`; Settings shows it under the title and clears it after 3 seconds. No route parameters.
7. **The switch is React Native's `Switch`.** The whole row is one accessible switch element (the inner `Switch` has `pointerEvents="none"`). Optimistic, disabled while saving, reverted with a message on failure, no confirmation.
8. **`BioInline` has one optional prop** (`label`, default off). It never reads or writes anything but `user.bio` and `PATCH /me {bio}`.
9. **The gear is mounted only when `edit && inTab`** in `ProfileForm.tsx` (never on the first-run page or sign-up), as the last child of the header row's right group, `space.sm` after the rule. Nothing else in that file changes.
10. **The Log out sheet is Phase 2's `ConfirmSheet`** (`LogOutSheet.tsx` is a thin wrapper: title 'Log out of RNDMRoll?', body "You'll need to sign back in.", rows 'Log out' and 'Stay logged in'), so no new `radius.lg` file exists. If the built `ConfirmSheet` has the per-row destructive flag (Phase 3 adds it) 'Log out' uses it; otherwise the row is plain ink.
11. **Radius lists are unchanged.** No `radius.full` and no `radius.lg` is used by any new file (Phase 2's `radius.lg` list of five files and `radius.full` list of four stay exactly as they are).
12. **Edit profile opens `profile/edit` as it is.** Its bottom button, while nothing has changed, still says Continue and goes to Today until Phase 4's `pushed` prop changes it. Noted here, not changed.
</binding_decisions>

<threat_model>
| Threat | Result | Why |
|---|---|---|
| A password ends up in a log, a route, a notice or a screenshot | Mitigate | Neither password is passed to `console`, a route parameter or the notice; the boxes are `secureTextEntry` unless Show is on; greps in Task 1 and 2. |
| The phone is signed out by a password change | Mitigate | The response's tokens go through `signIn(result)`; Group 3 step 11 proves the phone keeps working. |
| A wrong current password looks like a lost session | Mitigate | The server answers 400 with a field name, never 401; the page names the field. |
| The switch shows a value the server does not hold | Mitigate | Optimistic change, then `reloadUser()`; on failure it reverts; Group 5 checks the stored value with `GET /me`. |
| The gear appears on the first-run page or sign-up | Mitigate | Mounted only when `edit && inTab`; cold-launch case (c) and Group 6 step 20. |
| A launch file breaks | Mitigate | None is edited (grep); a cold launch is recorded after the routes exist. |
| The Bio box of the form and `BioInline` disagree | Mitigate | Both write `PATCH /me {bio}` and the session user is the one source (`reloadUser()`); Group 4 step 14. |
</threat_model>
