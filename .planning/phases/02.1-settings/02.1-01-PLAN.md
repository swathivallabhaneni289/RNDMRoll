<binding_decisions>
Final.
1. **Account visibility is a column on `users`, not a table.** `account_visibility text not null default 'public'` with the check `users_account_visibility_check` (in 'public', 'private'). Migration `0005_account_visibility` (Phase 2's is 0004). Its down file drops the constraint and the column. It carries no data of its own to preserve.
2. **Stored and shown only.** Nothing in the server reads the value except the profile bodies and the sign-up default. The Friends view and Global (Phases 5 and 6) read the AUTHOR's column; this plan writes no query for that.
3. **The under-18 default is ONE function.** `user.DefaultVisibility(age int) string` in `internal/user/visibility.go` returns 'private' when `age < user.PrivateUnderAge` (18) and 'public' otherwise; sign-up calls it with `user.AgeOn(birth, now)`. Dropping the rule means making it return 'public'. It is a recommendation the developer can drop; say so in the summary.
4. **The setting rides on `PATCH /me`.** `UpdateProfileRequest.AccountVisibility *string`, `ProfilePatch.AccountVisibility *string`, `coalesce` in the one UPDATE. No new route for it.
5. **Change password is a new route on the signed-in group:** `POST /v1/me/password`, in a new `AccountHandler` (new file), registered nil-safely in `NewServer` (`if deps.Account != nil`), so the existing test builders that do not set it keep working.
6. **The password change is one transaction in the Postgres repository** (`UserRepo.ChangePassword`: update the hash, revoke every active refresh token of the account, insert one new token). The raw token is made in `internal/auth` (`RefreshService.IssueInTransaction`), never in the repository. The narrow interface `user.PasswordChanger` is implemented only by the Postgres repository and the httpapi fake, so the three other `user.Repository` fakes are not touched.
7. **Order inside the handler:** caller, bind (400 or 413), `current_password` present, `new_password` by `passwordReason`, the current password compared (bcrypt; a missing hash compares against the dummy hash), the new password refused if equal to the current one, the new password hashed (bcrypt's 72 BYTES: too long is a field error on `new_password`), then the transaction, then the response. A wrong current password and an unchanged password are field errors with the new reasons `incorrect` and `unchanged`.
8. **Response:** the same body as log in (`access_token`, `refresh_token`, `expires_in`, `user`), built with the same `apiUser`. The caller's own session continues on the new tokens; every other refresh token is revoked at once; other phones' access tokens expire within `AccessTokenTTL` (15 minutes).
9. **Limits:** `PATCH /me` 30 a minute per caller (`KeyBySubject`); `POST /me/password` 5 a minute per caller (`KeyBySubject`) AND 20 a minute per address (`KeyByIP`). The 429 body is the existing `{"error":"rate_limited"}`.
10. **No password in a body, a log line or an error text.** The handler logs nothing about the request. Tests prove it.
11. **`NewUserRepo` returns `*UserRepo`** (it still satisfies `user.Repository`) so `main.go` can pass the same value as a `PasswordChanger`.
12. The Phase 1 sign-up, log in, refresh, log out, username and avatar behaviour does not change.
</binding_decisions>

<threat_model>
| Threat | Result | Why |
|---|---|---|
| Password change used to take over an account with a stolen access token | Mitigate | The CURRENT password is required, compared with bcrypt, limited to 5 a minute per caller and 20 a minute per address. |
| A change leaves an attacker's other session alive | Mitigate | Every active refresh token is revoked in the same transaction that stores the hash; only the new token lives. Other access tokens die within 15 minutes. |
| Half a change (new hash, old sessions alive, or no session at all) | Mitigate | One transaction; a failed insert rolls back the hash (test). |
| Wrong-password answers reveal anything | Mitigate | Only the caller's own account is involved; the answer is the same 400 for a wrong current password however it is wrong; a missing hash compares against the dummy hash. |
| A password in a response, a log line or an error | Mitigate | The handler logs nothing about the request; a test scans bodies and the log buffer. |
| A 401 on a signed-in call signs the phone out | Mitigate | A wrong current password is a 400 field error, never a 401. |
| A person sets another person's visibility | Mitigate | The id comes only from the token; `PATCH /me` has no id in the body; a test with two accounts. |
| An invalid visibility stored | Mitigate | `ValidVisibility` before the query and the check constraint after it (mapped to a field error). |
| Existing accounts change by surprise | Mitigate | `add column ... default 'public'` rewrites no value; the cutover reads the count of non-public rows (0) and never edits accounts. |
| Username grabbing by a loop of PATCH /me | Mitigate | 30 a minute per caller on top of the 90 a minute per address on the availability check; the unique index still decides. |
</threat_model>
