<threat_model>
| Threat | Result | Why |
|---|---|---|
| One account sees another account's cached cards after a switch | Mitigate | The Board and post caches are keyed by the user id and cleared when it changes or on sign-out (binding decision 7). |
| The phone decides who may see a post, or what the day in play is | Mitigate | The visibility rule, the gate and the day in play are server-only (contract). The phone draws `state`, `days` and `locked` as sent; no clock, no date maths and no `Date` at all (greps); every time label is the server's string. |
| A double tap sends two reactions or two comments | Mitigate | A ref blocks a second request while one runs; a reaction is idempotent (set, not toggle) on the server; a comment send clears the field only on success. |
| A reaction on your own post | Mitigate | The row is not drawn for `card.mine`; the server refuses with `own_post` anyway. |
| Emoji leaking into screen furniture or a second file holding the names | Mitigate | The characters and names live in `lib/entry/reactions.ts`; the scan allows only that file; no reaction name is typed elsewhere (grep). |
| A post of a blocked or removed person lingers | Mitigate | The Board and post reload on focus; a 404 shows the gone state; nothing is cached across users. |
| Launch breaks (Unmatched Route, Welcome flash, a sixth tab) | Mitigate | The only layout edit is `app/(app)/_layout.tsx`; hidden routes use `href: null`; one cold launch is recorded and the item count is checked. |
| Back from a post lands on the wrong tab | Mitigate | `backBehavior="history"` and a device check in plan 05-06 Task 3 (Board to post to Back, Notifications to post to Back); the documented fallback is a paper edit. |
| A huge or slow list | Accept | Five days a page and endless scrolling; a friend group has a few cards a day. |
| Photo links are public until real storage | Accept, flagged | The server builds links through one function (plan 05-02); the bucket is public in test mode. Flag before any outside user. |
