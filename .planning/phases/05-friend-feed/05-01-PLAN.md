   - `friend_requests`: `id uuid pk default gen_random_uuid()`, `from_user`, `to_user` (both `references users(id) on delete cascade`), `created_at timestamptz not null` (from Go, no default); check `from_user <> to_user`; a UNIQUE INDEX on `(least(from_user, to_user), greatest(from_user, to_user))`, so there is at most one pending request per pair of people, in either direction; indexes `(to_user, created_at desc)` and `(from_user, created_at desc)`.
   - `friendships`: `user_low`, `user_high`, `requested_by` (all `references users(id) on delete cascade`), `created_at timestamptz not null` (the time it was accepted); `primary key (user_low, user_high)`; check `user_low < user_high`; check `requested_by = user_low or requested_by = user_high`; indexes `(user_high)` and `(requested_by, created_at desc)`.
   - `blocks`: `blocker_id`, `blocked_id` (both `references users(id) on delete cascade`), `created_at timestamptz not null`; `primary key (blocker_id, blocked_id)`; check `blocker_id <> blocked_id`; index `(blocked_id)`.
3. **A pending request is a row. Resolving it (accept, decline, cancel, block) deletes the row.** There is no status column and no history, so a decline is silent and the sender can ask again later.
4. **A friendship is one row for the pair, low id first.** The order is the canonical lower-case text form of the uuid, which sorts exactly as Postgres sorts the `uuid` type; a test proves the Go order and the database order agree.
5. **A pair action runs in one transaction under an advisory lock on the pair** (`pg_advisory_xact_lock(hashtextextended('friends:' || low || ':' || high, 0))`), taken before anything is read. So accept against cancel, two requests crossing, and block against accept cannot interleave. The in-memory repository uses one mutex.
6. **Lookup is by exact username only**, case-insensitive, with one leading `@` allowed: never by email, never by name, never partial. The username shape is the one the database and the sign-up page already enforce (`^[a-z0-9_]{3,20}$` after lower-casing). A shape that cannot be a username is a 400 field error; a well-formed miss, yourself, and any pair where either person blocked the other are all 404 `not_found` with the same body.
7. **The visibility rule is a pure function** in `internal/social/visibility.go` (Task 1). `CanView(Facts)`: the owner always; otherwise nobody who is blocked either way; otherwise accepted friends who have a posted day of their own for the entry's `local_date`. `CanReact` is `CanView` and not the owner. `CanComment` is `CanView`. Phase 6 adds one more row (a public owner) in this one function and nowhere else. The public or private choice is Phase 2.1's `users.account_visibility` (default public) and NOTHING in Phase 5 reads it: `CanView` stays friends-only, and Phase 6 adds the public branch.
8. **Limits.** At most 50 pending outgoing requests per person (the 51st is `request_limit`, 409). Rate limits are per person and per minute: lookup 30, ask 10, accept, decline, cancel, remove, block and unblock 20 each, the friends list 60.
9. **Error codes.** New: `already_friends` 409, `request_exists` 409, `request_limit` 409 (an addition to the code list in 05-CONTEXT; the app message is "You can't send more requests right now. Cancel one first."). Reused: `not_found` 404, `validation_failed` 400, `profile_incomplete` 403, `rate_limited` 429, `payload_too_large` 413. `errors.go`, `spin_errors.go` and `entry_errors.go` are not edited.
10. **Time.** No `time.Now()` in new code. `now` comes from `clock.Clock.NowFor(callerID)`, read once per call after the lock. (The existing rate limiter reads the real clock; that is not new code.)
11. **Test fixtures** exist only when `cfg.SpinTestTools` is true, only for accounts on `SPIN_TEST_USER_EMAILS`, and only between TWO listed accounts. A relation with an account that is not listed (a real one) is never created, changed or cleared by any test tool.
12. **Nothing here deletes an account or touches the four real dev accounts.** Every table cascades from `users`, so the `truncate users cascade` cleanups of the test suites clear them.

**c. Service** (`internal/social/service.go`; `NewService(repo, posted PostedDays, clk clock.Clock)`). Each call that writes reads `now` once, after the lock.
- `Lookup(ctx, viewer, raw)`: `CleanUsername` (a `*FieldProblem` is returned as is); `FindByUsername`; the person is the viewer, or `HasBlock` either way: `ErrNotFound`; else the `Relation`.
- `SendRequest(ctx, viewer, raw)`: as `Lookup` up to the target; then `InPairTx`: re-check the block (`ErrNotFound`); a friendship is `ErrAlreadyFriends`; a pending request FROM the viewer is `ErrRequestExists`; a pending request FROM the target is accepted instead (delete it, insert the friendship with `requested_by` = the target) and returns `friends`; else `OutgoingCount` at 50 is `ErrRequestLimit`; insert the request at `now` and return `request_sent`.
- `Accept(ctx, viewer, requestID)`: read the request (missing: `ErrNotFound`), then `InPairTx` on its pair and read it again by id under the lock (gone, or `to_user` is not the viewer: `ErrNotFound`); a block between the two deletes the request and is `ErrNotFound`; delete the request, insert the friendship (`requested_by` = `from_user`, `created_at` = `now`); return `friends`.
- `Decline` (viewer is `to_user`) and `Cancel` (viewer is `from_user`): the same read-lock-read; delete; wrong person or gone is `ErrNotFound`. Nobody is told.
- `Remove(ctx, viewer, other)`: `other` equal to viewer is `ErrNotFound`; delete the friendship in a pair transaction; absent is fine (idempotent). Blocks and requests are not touched.
- `Block(ctx, viewer, other)`: `other` equal to viewer or not an account is `ErrNotFound`; in one pair transaction: insert the block, delete the friendship, delete every request between the two. A repeat is fine.
- `Unblock(ctx, viewer, other)`: delete the block; absent is fine. Nothing else comes back.
- `List(ctx, viewer)`: friends ordered by lower-cased name then username; incoming and outgoing newest first; blocked newest first; every list carries `Person`s from one `People` read.
- `FriendCount(ctx, userID)`, `FriendIDs(ctx, userID)`: for plans 05-02 and 05-03.
