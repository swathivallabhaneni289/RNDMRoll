<threat_model>
| Threat | Result | Why |
|---|---|---|
| Using Find to probe usernames at speed | Mitigate | The server limits lookups to 30 a minute. The app finds only on the button or Return, never while typing, and answers a non-username locally. A hit confirms a username exists, which a friend finder cannot avoid. |
| A double tap sends two requests or two accepts | Mitigate | A busy flag per row blocks a second tap; the server answers a repeat with `request_exists` or 404, which the screen treats as the settled state. |
| Removing or blocking a friend by accident | Mitigate | Each asks once on its own sheet; nothing is sent before the confirming row. |
| The phone invents a relation | Mitigate | After every action the lists are reloaded from the server; the Find result's relation comes from the server's answer. |
| Another account's lists after a sign-out | Mitigate | No module store: the screen holds its data in component state, so a sign-out unmounts it. |
| An odd name or username breaking a row | Mitigate | Plain text, one line, cut with an ellipsis; the avatar initial is taken by code point. |
| Launch breaks (Unmatched Route, Welcome flash) | Mitigate | No launch file is edited; the one new route sits in the Profile stack; one cold launch is recorded. |
| New native module needed | Mitigate | None added; the share sheet is React Native's own `Share`. `package.json` is unchanged (acceptance). |
| Round shapes spreading | Mitigate | One new file names `radius.full` (`Avatar.tsx`); chips are Phase 4's `Chip` (scans). |
</threat_model>
