<binding_decisions>
Final.
1. Migration 0007 (Phase 1's clean-up is 0003, Phase 2's 0004, Phase 3's 0005, Phase 5's 0006; hand numbered; never `migrate create -seq`; re-check with `ls migrations` and rename if the built numbers differ) adds `account_settings`, `post_reports`, `comment_reports` and one index. Nothing in `users`, nothing else in `entries` or in Phase 5's comments table.
2. `account_settings (user_id pk references users(id) on delete cascade, visibility text not null default 'private' check in ('private','public'), updated_at timestamptz not null)`. A missing row means Private. The row is written by the first change. Its `updated_at` comes from Go, no trigger.
3. **Effective public** = the row says `public` AND the owner is 18 or over on the date the read uses. One rule in Go (`account.IsAdult(birthday, on)`) and one SQL form (`age(<the owner's local date>, u.birthday) >= interval '18 years'`), proved equal by a table of dates (Task 1e, Task 2f). In both, `on` is the OWNER'S local date: the caller's clock instant converted with the owner's stored zone (`user_time_zones`, else UTC). So the PATCH check, the Global list, the person page and the single-post facts all judge the same person by the same date, and nobody is judged by a date from another zone.
4. `PATCH /v1/account/visibility` to `public` is refused with 403 `under_age_for_public` when the owner is under 18. To `private` it always works. A repeat is a 200 with the same shape. `can_be_public` is true when the owner is 18 or over.
5. The visibility rule (the one function): `CanView = IsOwner || (!Blocked && ((AreFriends && ViewerPostedThatDate) || OwnerPublic))`. Reading a post's comments and writing one need exactly `CanView` (`CanSeeComments = CanComment = CanView`): whoever can see a post can read and write its comments, so a stranger may comment on a public post and a blocked pair can do neither. `CanReact = CanView && !IsOwner`. A comment's `can_delete` is the writer or the post's owner (Phase 5's rule, unchanged). `ViewerPostedThatDate` is a `posted_days` row for the entry's `local_date` (any source), as in Phase 5.
6. Not visible answers 404 `not_found` with the same body as a missing id, on every route. Ids are UUIDs parsed in Go; a non-UUID is 404.
7. Global: `GET /v1/board?view=global`. Entries of effectively public owners, newest first by `entries.created_at` then `id`, keyset paging on `(created_at, id)`, 20 by default, 1 to 40. Excludes the viewer's blocks in both directions and every entry the viewer reported. Includes the viewer's own public posts (`mine` true). Not gated.
8. Person: `GET /v1/people/{user_id}`. 404 for the caller's own id, an unknown id, a blocked pair (either way), and anyone who is not effectively public, not a friend and has no request with the caller. Otherwise the person, the `relation`, the `visibility` ('public' only when effective), and `posts`: the same cards as Global for that owner when effectively public, else null.
9. Report: `POST /v1/posts/{entry_id}/report` with `reason` one of `spam`, `unkind`, `not_public`, `other`. The reporter must be able to view the post (else 404) and must not own it (409 `own_post`, Phase 5's code). One report per person per post: a repeat is a 200 and stores nothing new. The post disappears from that reporter's Friends board, Global and person lists at once (every list query excludes it for that reporter). A direct fetch of the post by its id still works (the owner and others are unaffected). Nothing is hidden, removed or counted automatically.
10. Photo links: Phase 5's single link function is extended, not duplicated: it builds a link only for an entry the visibility function allows for that viewer. Real friend-only or signed links still wait for the real storage account (launch list).
11. Cursors are opaque (URL-safe base64 of the created time and the id), validated on decode (a bad one is 400 `cursor` invalid). They carry a position only, never permission.
12. Time: no `time.Now()` in new code. `now` comes from the per-account clock accessor the spin service uses, once per call.
13. The test reset also clears the caller's `post_reports` and `comment_reports` (as reporter) and the caller's `account_settings` row (back to Private). Reports on the caller's own posts and comments go with the entries and comments (cascade).
14. No change to `internal/user`, `ApiUser`, `/me`, sign-up, the avatar flow, `s3.go`, `errors.go` or `spin_errors.go`.
15. Comment report: `POST /v1/comments/{id}/report` with `reason` one of `spam`, `unkind`, `other` (`not_public` is `invalid` here). The reporter must be able to view the comment's post (else 404) and must not be the comment's writer (409 `own_comment`, a new code). One report per person per comment: a repeat is a 200 and stores nothing new. The comment is left out of that reporter's comment lists and counts at once; everyone else, the writer and the owner included, still sees it. The post's owner may report too (the app shows them 'Delete' instead, so only a hand-made request reaches it). Nothing is hidden, removed or counted automatically.
16. Blocked writers: a comment written by anyone blocked with the viewer (either way) is left out of the viewer's comment lists and counts, and a blocked pair cannot read or write comments on each other's posts (the post itself is 404 for them).
17. **Delete and block is not a server feature.** The app (plan 06-02) deletes a comment that is not the caller's with Phase 5's `POST /v1/comments/{id}/delete` and then blocks its writer with Phase 5's `POST /v1/blocks`, two existing calls in that order. Nothing new is added to the server for it and there is no transaction across the two calls. If the block call fails after the delete succeeded, the comment stays deleted (a delete has no undo), the writer is not blocked and nothing on the server tries to repair that: the app says so and offers the block again, and a repeat block is harmless (a block of an already blocked pair is a 200 in plan 05-01; record the built answer in the summary). If the delete fails, the app sends no block.
</binding_decisions>

| Threat | Result | Why |
|---|---|---|
| A stranger or a private account reads a private post or its photo | Mitigate | One visibility function, used by every read and by the single photo-link function. Everything not visible is 404. Proved by the equivalence matrix over the function, the post fetch and the list queries. |
| Probing ids to learn who exists or who is private | Mitigate | A private stranger, a blocked pair and an unknown id return the same status and body. Ids are UUIDs parsed in Go. The lookup is rate limited (Phase 5). |
| An under-18 account becomes Public through the API | Mitigate | The PATCH refuses it (403) using the owner's local date; a crafted request gets the same answer. |
| An under-18 account is listed because a row says public (a stale row, a direct write, a changed birthday) | Mitigate | Every Global and person read re-checks the age in SQL. A test writes such a row by hand and proves it is never listed. Start rule 5 covers a birthday change. |
| Report flood or one person reporting everything | Mitigate | One report per person per post or comment (unique), 10 a minute, and the only effect is hiding the post or comment for that reporter. Nothing is removed for others. |
| Comment spam or abuse from strangers on a public post | Mitigate | Phase 5's 20 a minute comment limit and 140 characters apply to every writer; the owner can delete any comment on their post; anyone can report a comment (hidden for them at once) or block its writer; nothing is automatic. A per-day cap and an owner switch to turn comments off are deferred. |
| A private non-friend reads or writes the comments of a private post | Mitigate | Comments use the post's visibility function: the post, its comment list and a comment create all answer 404. |
| A blocked person's words still reach the blocker, or a blocked pair keeps talking | Mitigate | Comment lists and counts leave out comments written by anyone blocked with the viewer, and a blocked pair can neither read nor write comments on each other's posts. |
| A comment report used to silence someone for everybody | Mitigate | A report hides the comment only for the reporter; nothing is removed or counted for others. |
| A stranger's reaction or comment never reaches the owner's bell, or a blocked person's does | Mitigate | The derived list has no friendship condition for reaction and comment items and excludes blocks both ways; one test over HTTP (start rule 6). |
| Delete and block half done (the delete succeeds, the block call fails) | Accept, flagged | Two existing calls, no transaction. The comment stays deleted and the writer is not blocked; the app says so and retries only the block. A one-call route would need a new server contract; not worth it for a friend-group test. |
| A response leaks `photo_key`, birthday, email, a password hash or a friend code | Mitigate | The response-scan test over every Phase 6 route; `Person` has a fixed key set. |
| A blocked person still sees or is seen | Mitigate | Blocks are read in both directions in the visibility rule and in every list query; tests for Global, the person page and the post fetch. |
| The reporter keeps seeing the post through another list | Mitigate | The reported filter is in the Friends, Global and person queries (one test each). |
| Scraping Global with a signed-in account | Accept, flagged | The posts are public by the owner's consent; reads need a token, are rate limited and cannot be searched. No bulk export. Flag before any outside user. |

| A cursor is tampered with | Mitigate | It is validated on decode and carries a position, not permission; every page re-applies the full predicate. |
| A race between two changes of the setting | Accept | An upsert; the last write wins; both answers are valid states. |
