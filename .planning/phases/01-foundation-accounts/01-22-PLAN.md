# 01-22: log in with an email or a username


## Why

On 2026-10-09, during the Phase 1 close-out, the developer said a person who picked a username at sign-up should be able to use that username and the password to log in. Claude read it as the way Instagram does it: one box that takes either, same password. Sign-up stays as it is. Email stays on the account because Forgot password and email verification (both on the launch list) need it.

## Design

- **One box.** The Log in page's first box is labelled "Email or username". Text with an @ is an email address; anything else is a username (an email can never be a username, so there is no ambiguity). The password box is unchanged.
- **Client checks.** Empty: "Enter your email or username." Has an @ but does not look like an address: "Enter a valid email address." Anything else is left to the server, so a username that does not exist gets the same message as a wrong password.
- **Server.** `POST /v1/auth/login` takes `login` (email or username). `email` is still accepted as the older name for the same field and `login` wins if both are sent. An email-shaped or empty login is checked with the sign-up address rule and a bad one is a 400 naming the field `login`. A username is looked up ignoring case (`GetByUsernameCI`, same index as the availability check). Text that could never be a username (spaces, punctuation, shorter than 3, longer than 20) is treated as an unknown account, not a format error.
- **Enumeration resistance unchanged.** Unknown username and wrong password both run a bcrypt comparison (dummy hash for the unknown case) and return the identical `invalid_credentials` body.
- **Limits.** The old 5 a minute per address and login stays (keyed on `login`, falling back to `email`, capital letters ignored). New: 20 a minute per address in total, because a username is shown to friends (unlike an email) and one address should not be able to try many of them.
- **Message.** `invalid_credentials` now reads "That email, username or password isn't right."
- **Autofill.** The box tells iOS it is a username field (`autoComplete` and `textContentType` "username"), so saved logins of either kind are offered.

## Tasks

1. **Server.** Done 2026-10-09. New repository method, handler change, two limiters, 16 new test cases across handler, full-server, middleware, Postgres and end-to-end (real Postgres) tests. Gates: `go build`, `go vet`, `go test ./... -p 1` on `rndmroll_test` all pass.
2. **App.** Prepared in a separate copy of the project (so the phone does not reload mid-test) and type-checked there (`tsc` exit 0). Applied to the main tree and the API restarted only at a boundary, with the phone relaunched, never while the developer is mid-flow.
3. **Walkthrough.** The developer logs in with the email, then with the username (also in capital letters), then with a wrong password and an unknown username.
4. **Commit** only after the developer has seen it. Never push.

## Not in this plan
