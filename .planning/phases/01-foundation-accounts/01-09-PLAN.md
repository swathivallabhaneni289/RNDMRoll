`internal/mail/mailer.go` in package `mail` declares `type Mailer interface { SendVerificationEmail(ctx context.Context, u *user.User) error }`, matching the consumer interface plan 01-08 declares at its point of use so the concrete type satisfies both without either package importing the other.

It also exports `type Service struct` implementing that interface, constructed by `NewService(repo user.EmailVerificationRepository, sender Sender, baseURL string, ttl time.Duration)`. `Sender` is the narrower transport contract `interface { Send(ctx context.Context, to, subject, html, text string) error }`, which is what makes the provider swappable. RESEARCH.md Open Question 2 explicitly recommends designing this package behind an interface so the concrete provider can change without touching callers.

`Service.SendVerificationEmail` calls `DeleteForUser` to supersede any outstanding token, reads 32 bytes from `crypto/rand`, encodes them with `base64.RawURLEncoding` as the link token, stores `sha256.Sum256` of the raw bytes with an expiry of now plus the TTL through `Insert`, builds the link as `{baseURL}/v1/auth/verify-email/callback?token={token}`, and hands a subject and body to the `Sender`. Only the digest is stored. RESEARCH.md Pitfall 5 requires exactly this combination of hashed storage, expiry, and single use so a forwarded or leaked message cannot verify an account weeks later.

Message copy, held to PROJECT.md's no-em-dash and no-AI-slop constraints: subject `Verify your email for RNDMRoll`; body `Tap the link below to verify your email and finish setting up your account.` followed by the link and `This link expires in 24 hours. If you did not sign up, you can ignore this message.` Provide both an HTML and a plain-text part.

`internal/mail/resend.go` exports `NewResendSender(apiKey, fromAddress, fromName string) Sender`. `Send` posts JSON to `https://api.resend.com/emails` with an `Authorization: Bearer` header and a body carrying `from`, `to`, `subject`, `html`, and `text`. Use a `*http.Client` with a 10 second timeout. Treat any non-2xx as an error carrying the status code but not the response body, so a provider error message cannot flow into a user-facing response. Resend was selected at planning time from the two candidates RESEARCH.md named; the delegation was explicit, and Resend needs no AWS sandbox exit and no SDK dependency, only a single HTTPS POST.

`internal/mail/log_mailer.go` exports `NewLogSender(out io.Writer) Sender`, which writes the recipient and the full link to the writer and returns nil. This is the driver selected when `MAIL_DRIVER=log`, which the plan 01-01 checkpoint offers as a way to run the whole phase before a Resend account exists. It is a first-class configuration for local development, not a stand-in for unfinished work: the token flow, expiry, and single-use enforcement are identical on both drivers.

Tests cover the five behaviors with a fake `Sender` capturing the last message and the in-memory verification repository fake.

Create `internal/httpapi/verify_email.go` with `VerifyEmailHandler` holding a `user.Repository`, a `user.EmailVerificationRepository`, a `mail.Mailer`, a `*auth.RefreshService`, the JWT secret and access TTL, and the deep-link scheme. Its `Register(rg *gin.RouterGroup)` mounts three routes and touches no file another wave 4 plan owns.

`Verify` binds `{ Token string \`json:"token" binding:"required"\` }`, hashes it, and calls `ConsumeByHash`, which atomically marks the row consumed and returns the owning user ID. Propagate `ErrTokenConsumed`, `ErrTokenExpired`, and `ErrTokenInvalid` through `RespondError` to the codes the client branches on. On success call `MarkEmailVerified` with `user.VerifiedViaPasswordFlow`, then mint the user's first access and refresh token pair and respond 200 with the full `AuthResult` shape including the user object. This is the moment a password-path account first holds a session: D-05 puts verification at step 2, before the name, username, and photo steps, so those steps run as authenticated requests.

`Resend` binds `{ Email string \`json:"email" binding:"required,email"\` }`, looks up the account, and calls `SendVerificationEmail` when it exists and is unverified. It responds 202 with an identical body in every case, including an address with no account and an address already verified. Returning a different status or body for a registered address would make this endpoint an account-existence oracle, which RESEARCH.md's Security Domain lists as an enumeration vector alongside login.

`Callback` handles `GET /v1/auth/verify-email/callback?token=...`. Mail clients open links in a browser, not in the app, so this route returns a minimal HTML page that immediately redirects to `{scheme}://verify-email?token={token}` and also renders a plain tappable link as a fallback for browsers that block automatic scheme navigation. It performs no verification itself: the token is consumed only when the app posts it to `Verify`, which keeps the single-use consumption tied to the device that started the signup. HTML-escape the token before interpolating it into the page.

`Register` attaches `RateLimit(LimitConfig{Requests: 1, Window: 30 * time.Second, KeyFunc: KeyByIPAndField("email")})` to the resend route. The 30 second window matches UI-SPEC's client-side resend cooldown exactly, so the visible countdown and the server limit agree rather than the user hitting an unexplained 429 after the timer reaches zero.

Tests cover the six behaviors, asserting byte-identical resend responses for registered and unregistered addresses.

Create `internal/middleware/verified.go` exporting `RequireVerified(repo user.Repository) gin.HandlerFunc`. It runs after `RequireAuth`, reads the subject through `SubjectFromContext`, loads the account, and aborts with 403 and the body `{"error":"email_not_verified"}` when `EmailVerified` is false. A subject that resolves to no account aborts with 401 `token_invalid`, which covers a token minted for an account since deleted.

Store the loaded `*user.User` in the request context under a typed key and export `UserFromContext(c *gin.Context) (*user.User, error)` so downstream handlers reuse the record instead of issuing a second lookup for the same row.

This middleware is what makes D-04 a system property. The onboarding UI already declines to advance an unverified user, but a gate at the route boundary means a direct API call cannot bypass the decision either. Plan 01-11 attaches it to every profile route, and plan 01-13 attaches it to the authenticated route group as a whole.

Note the deliberate asymmetry with social sign-in: an Apple or Google account is created with `email_verified` already true and a provider verification source, because those providers verify the address before issuing the identity token. Such accounts pass this gate on their first request without ever receiving a verification email, which is the branch of RESEARCH.md Open Question 1 this phase adopts.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| app -> email provider | Account addresses leave the system in outbound mail |
| email inbox -> API | A token arrives from an out-of-band channel |
| session -> verified-only routes | An authenticated but unverified session is still untrusted |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-01-VER-01 | Spoofing | verification token reuse or an indefinitely valid link | high | mitigate | 32 bytes of `crypto/rand`, stored only as a SHA-256 digest, 24 hour expiry, consumed marker set atomically by `ConsumeByHash`, and outstanding tokens deleted on resend; this is RESEARCH.md Pitfall 5's full mitigation |
| T-01-VER-02 | Information Disclosure | resend endpoint as an account-existence oracle | high | mitigate | Byte-identical 202 for registered, unregistered, and already-verified addresses, asserted in test |
| T-01-VER-03 | Elevation of Privilege | unverified session reaching app routes | high | mitigate | `RequireVerified` rejects with 403 at the route boundary, so D-04 does not depend on client routing |
| T-01-VER-04 | Tampering | HTML injection through the token in the browser callback | high | mitigate | Token is HTML-escaped before interpolation into the redirect page |
| T-01-VER-05 | Denial of Service | resend used to generate mail volume or cost | medium | mitigate | 1 request per 30 seconds keyed by IP and address, matching the client cooldown so the limit is never a surprise |
| T-01-VER-06 | Information Disclosure | provider error text reaching the user | medium | mitigate | The Resend adapter's error carries the status code only, never the response body |
| T-01-VER-07 | Spoofing | a hostile app claiming the rndmroll scheme and intercepting the callback redirect | medium | accept | Tokens are single-use and short-lived, and the interceptor would still need the victim's device. Promoting the callback to an HTTPS universal link is recorded as follow-up, not built in this phase. |
</threat_model>
