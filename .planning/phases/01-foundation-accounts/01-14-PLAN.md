  <action>
Create `lib/api/profile.ts` exporting `fetchProfile(): Promise<ApiUser>` calling `GET /v1/me`, `updateProfile(patch: ProfilePatch): Promise<ApiUser>` calling `PATCH /v1/me`, and `uploadAvatar(localUri: string, contentType: string, contentLength: number): Promise<string>` returning the public URL.

`ProfilePatch` is `{ name?: string; username?: string; bio?: string; avatar_url?: string }`, where an omitted key means unchanged, matching the nil-means-unchanged contract the server implements. `updateProfile` must send only the keys that actually changed, so saving a bio never rewrites a username and cannot trip a spurious username conflict.

`uploadAvatar` performs the same three steps the photo onboarding step performs: request a ticket from `POST /v1/me/avatar/upload-url`, `PUT` the binary to the returned `upload_url` with a matching `Content-Type` header, and return the `public_url`. It does not itself call `PATCH /me`; the caller decides when to persist, which is what lets the edit screen batch an avatar change together with a name change into a single save.

Surface a 409 `username_taken` as an `ApiError` carrying its `suggestions` array through unchanged, so the edit screen can render the same taken state the onboarding username step renders.
  </action>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| user input -> durable profile | Name, username, and bio become persistent identity |
| device library -> object storage | A user file leaves the device |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-01-PRV-01 | Elevation of Privilege | editing another account's profile | high | mitigate | Both screens call `GET` and `PATCH /me` only; plan 01-11 exposes no route that accepts a user identifier, so no request these screens can construct addresses another row |
| T-01-PRV-02 | Spoofing | username claimed between check and save on the edit screen | medium | mitigate | The 409 insert-time conflict is handled as a designed state with fresh alternates, identical to the onboarding step |
| T-01-PRV-03 | Information Disclosure | a session left live on a shared device | medium | mitigate | Log out is reachable from the profile screen, confirmed through the contract's sheet, and `signOut` deletes both keychain entries and revokes the refresh token server-side |
| T-01-PRV-04 | Tampering | oversized bio bypassing the client cap | medium | mitigate | The 160 character cap is enforced at the input, at the server validator binding, and by the database check constraint from plan 01-03 |
| T-01-PRV-05 | Denial of Service | oversized avatar upload | medium | mitigate | Type and size bounds are bound into the presigned request by plan 01-11, so the storage provider enforces them regardless of client behavior |
| T-01-PRV-06 | Information Disclosure | avatar URL guessable across accounts | low | accept | Object keys carry a random component, and avatars are public-read by design since Phase 5 will show them in a friend feed |
</threat_model>
