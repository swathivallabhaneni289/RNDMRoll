`lib/onboarding/draft.ts` exports a small module-scoped store with `setDraft(patch: Partial<OnboardingDraft>)`, `getDraft(): OnboardingDraft`, `clearDraft()`, and a `useDraft()` hook. `OnboardingDraft` is `{ email?: string; suggestedName?: string; provider?: 'email' | 'apple' | 'google' }`. This is deliberately in-memory only and never touches SecureStore: it holds the address to display on the waiting screen and the name Apple hands back on a first authorization, neither of which is a credential.

`suggestedName` exists because of RESEARCH.md Pitfall 1b: Apple returns `fullName` and `email` only on a user's very first authorization for a given Apple ID and bundle ID, and returns null on every subsequent call. The value must be captured at that moment and carried into the D-05 step 3 name screen, which plan 01-12 prefills from here.

`lib/auth/social.ts` exports `isAppleSignInAvailable(): Promise<boolean>` wrapping `AppleAuthentication.isAvailableAsync()`, `signInWithApple(): Promise<AuthResult>`, and `signInWithGoogle(): Promise<AuthResult>`.

`signInWithApple` calls `AppleAuthentication.signInAsync({ requestedScopes: [FULL_NAME, EMAIL] })`, then posts `{ identity_token: credential.identityToken, full_name: <joined givenName and familyName or null> }` to `POST /v1/auth/oauth/apple`. It sends the raw `identityToken` string and nothing else that asserts identity. RESEARCH.md Pitfall 3 and PATTERNS.md's shared pattern both state the backend must accept only the raw provider token, never a client-shaped identity payload, because a modified client could otherwise claim any address. `full_name` is sent as a convenience prefill only and the backend treats it as untrusted display text, not as an identity claim. Catch the `ERR_REQUEST_CANCELED` error code and return a sentinel the caller can recognize, since UI-SPEC's social sign-in contract requires a user-initiated cancel to return silently to idle with no error shown.

`signInWithGoogle` calls `GoogleSignin.configure({ iosClientId, webClientId })` once at module load reading `process.env.EXPO_PUBLIC_GOOGLE_CLIENT_ID_IOS` and `EXPO_PUBLIC_GOOGLE_CLIENT_ID_WEB`, then `GoogleSignin.hasPlayServices()` and `GoogleSignin.signIn()`, and posts `{ id_token: response.data.idToken }` to `POST /v1/auth/oauth/google`. Handle `SIGN_IN_CANCELLED` the same way as the Apple cancel path.

Both functions write `provider` and, for Apple, `suggestedName` and `email` into the draft before returning, then leave the session handoff to the calling screen.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| user input -> backend | Email and password leave the device |
| provider SDK -> backend | Apple and Google identity tokens pass through the client |
| email inbox -> app | A verification link re-enters the app through a deep link |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-01-ONB-01 | Spoofing | forged social identity from a modified client | high | mitigate | `lib/auth/social.ts` transmits only the raw `identityToken` or `idToken`; the verify gate asserts no client-asserted email or provider field is sent to the oauth endpoints, and plan 01-10 re-verifies signature, issuer, audience, and expiry server-side |
| T-01-ONB-02 | Information Disclosure | login response distinguishing unknown account from wrong password | high | mitigate | One generic message rendered for every 401 `invalid_credentials`; the server never returns a distinguishing code |
| T-01-ONB-03 | Information Disclosure | password captured by keyboard or autofill heuristics | medium | mitigate | `secureTextEntry` plus explicit `textContentType` and `autoComplete` so the OS password manager handles the field rather than the generic text path |
| T-01-ONB-04 | Tampering | a hostile app registering the same deep-link scheme and capturing a verification token | medium | mitigate | Verification tokens are single-use and expire in 24 hours (plan 01-09); the consumed marker means an intercepted token that has already been redeemed is inert. Promoting the link to an HTTPS universal link is recorded as follow-up rather than built here. |
| T-01-ONB-05 | Denial of Service | resend button hammered to send mail repeatedly | medium | mitigate | 30 second client cooldown backed by the matching server-side rate limit from plan 01-06, so disabling the client control is not the only barrier |
| T-01-ONB-06 | Information Disclosure | the waiting screen confirming an address is registered | low | accept | The address shown is the one the user just typed on this device, so no new information is disclosed; the resend endpoint itself returns 202 regardless of whether the account exists |
</threat_model>
