## Reviewer findings (as reported)

### security: fix-first
- [high] Account creation / Complete contract: The plan never requires a password for an email-kind sign-up. The contract lists `password?` as optional. The Complete order only says to hash a password and to reject one for social kind. A caller holding a valid email token can create a verified account with a NULL password_hash. Nothing in the API can recover that account, because there is no password reset and login needs a password. If the address had an empty legacy unverified row, that row is deleted in the same call, so the owner ends up with a dead account. Fix: In Complete, branch on the pending row's kind. Email kind: password is required (8 to 72 runes, then HashPassword, mapping ErrPasswordTooLong to field password), and an empty password gives 400 field password. Social kind: password must be absent. Add `TestIntegrationSignup_CompleteEmailKindWithoutPasswordIs400AndKeepsPending` and a social-kind test with a password.
- [medium] Targeted denial of someone else's sign-up (Start kills live tokens): Every successful Start sets token_hash, token_expires_at and verified_at to NULL. Anyone who knows an address can call start for it once the 60 s cooldown has passed (the IP+email limit allows 3 a minute). That kills the in-progress sign-up of the real person. The real person has passed the code step and is on Password, Birthday, Name or Username, and their next call returns 410 signup_expired. A new code does not weaken the proof that the mailbox was verified. The research only says a resend invalidates earlier codes, not tokens. Wrong guesses are also shared per address (5 per code, 15 an hour), so a stranger can burn the victim's tries and block the address for an hour. The threat model accepts that lockout. It does not mention the token kill. Fix: Start must not touch token_hash, token_expires_at or verified_at. A live token dies only by expiry, by Complete, or by the birthday refusal. If the plan wants one live token per address, issue the new token only on a successful verify, and keep the old one valid until then. Add a test: Start after verify leaves the token working.
- [medium] Email bombing a third party: All send caps (60 s cooldown, 5 an hour, 10 a day) are keyed on the exact lowercased address string. Plus-tags and Gmail dots (`victim+1@gmail.com`, `v.ictim@gmail.com`) are different keys that land in one inbox. The only other brakes are in-memory limits: IP 10 a minute, global 60 a minute. From one IP that is about 600 emails an hour to one victim, and it damages the sender reputation of the future real mail domain. The per-IP key is also raw ClientIP, so IPv6 /64 rotation bypasses it. Fix: Add a second cap keyed on a canonical mailbox: strip the +tag, and for gmail.com and googlemail.com remove dots. Count sends per canonical key in SQL (for example a small table or a column on pending_signups with its own hour and day windows). Also key the IP limiter on the /64 for IPv6. Lower the per-IP start limit to something like 10 an hour for distinct addresses.
- [medium] Apple sign-up abandoned and retried: Today an unknown Apple identity gets an account at once, so the email from the first authorization is stored. The plan keeps the empty-email refusal and only creates a pending row. If a person kills the app after the Apple sheet (before Create account) and taps Apple again, and Apple omits the email on the repeat, the call fails with 400 `validation_failed` (no email). The person cannot sign up with Apple until they revoke the app in iOS settings. The upsert would also overwrite the stored pending email with an empty one. The under-13 refusal deletes the pending row, so the same dead end applies there. Fix: On an unknown subject with an empty provider email, look up the pending row for (kind, subject) and reuse its stored email and issue a fresh token. The upsert must not overwrite email with an empty value (use coalesce(nullif($email,''), pending.email)). Add `TestIntegrationOAuth_AppleRetryWithoutEmailReusesPendingEmail`. Confirm on the simulator whether Apple's repeat identity token carries the email. If it never omits it, record that and drop this item.
- [medium] Migration 0004 and the old API binary: `0004_drop_email_verification_tokens` is in files_modified, but Task 19 says it ships later. `migrate up` (the Makefile target, Task 1 step 3, and both TestMain helpers) applies every file in `migrations/`. If the engineer creates the 0004 file in this change set, `migrate up` on rndmroll_dev drops the link-token table while the old `go run` binary is still serving. The old signup, verify and resend then fail with 500, and the plan's claim that the old binary keeps working until Task 17 is false. `TestMigrations_0002And0003AreReversible` uses `migrate down 2`, which would revert 0004 and 0003 instead of 0003 and 0002. Fix: Remove the two 0004 files from files_modified and from this branch. Write them in a later change. In Task 1 use `migrate ... up 2` for the dev database and name the exact versions. Make the reversibility test use `migrate goto` to explicit versions, not `down 2`.
- [medium] Limiter ordering and attacker-chosen keys: The plan lists the limits but not their order. The limiter map keeps one entry per key and runs an O(n) eviction loop under one global mutex on every request. If the IP+email limiter or the per-token limiter runs first, an attacker creates a new map entry per request by varying the email string or the X-Signup-Token header, and a key made from a random token is a fresh bucket each time, so the per-token limit does nothing against an unauthenticated flood. Each such request also costs a DB statement when RequireSignupToken slides the token. A request that is later refused for rate still slides the token. Fix: Fix the middleware order and write it in Task 5: global, then IP-only, then keyed-by-field, and for token routes IP limiter first, then RequireSignupToken (which only slides after a valid hash lookup), then the per-token limiter keyed by the pending row id, not by the raw header. Cap the map size in RateLimit or move eviction to a periodic sweep.
- [low] Request body size on unauthenticated endpoints: start and verify read the whole JSON body in the limiter key function (ShouldBindBodyWith) before any size limit. The server sets no MaxBytesReader, and ReadTimeout is 30 s. An anonymous caller can make the API buffer large bodies on endpoints that are now the main unauthenticated surface. Fix: Add a small middleware on /v1 that wraps `c.Request.Body` with `http.MaxBytesReader` (for example 16 KB) before the limiters, and add a test that a 1 MB body to /auth/signup/start returns 413 or 400.
- [low] Destructive test against the wrong database: The plan adds a test that runs `migrate down 2` then `up`. Down of 0002 drops the pending table and every stored birthday. The test pool comes only from the TEST_DATABASE_URL env var, and nothing checks the database name. The harness already truncates users, but this makes a wrong URL more destructive, and the dev database holds real test accounts. Fix: In both TestMain helpers and in this test, refuse to run unless the database name from the URL ends in `_test`. Do it before any truncate or migrate call.
- [low] Log driver prints live codes: The log mailer writes the full message, including the 6-digit code, to stdout, and the plan documents a grep on api.log. Config accepts MAIL_DRIVER=log in any environment, and the only guard against using it outside local development is a README note. Fix: When MAIL_DRIVER=log, config.Load should require an explicit opt-in such as `ALLOW_LOG_MAIL=1` (put it in .env.example for local use) and refuse to start otherwise. Add a config test for it.
