  <action>
Create `internal/httpapi/auth.go` in package `httpapi` with `type AuthHandler struct` holding a `user.Repository`, a `*auth.RefreshService`, a `Mailer` interface value, and the JWT secret plus access TTL. `NewAuthHandler(...)` constructs it. `func (h *AuthHandler) Register(rg *gin.RouterGroup)` mounts the routes and is the only place route paths appear, so no central router file is needed and this plan owns no file another wave 4 plan touches.

Declare the `Mailer` interface here as the narrow consumer contract `interface { SendVerificationEmail(ctx context.Context, u *user.User) error }`. Plan 01-09 implements it. Declaring it at the point of use rather than importing a package that does not exist yet is what lets these two plans run in the same wave.

Request DTOs use Gin binding tags as PATTERNS.md specifies: `SignupRequest{ Email string \`json:"email" binding:"required,email"\`; Password string \`json:"password" binding:"required,min=8,max=72"\` }` and `LoginRequest` with the same two fields. The `max=72` bound is bcrypt's hard byte ceiling from RESEARCH.md Pitfall 1, enforced at the validator layer so the hash call never sees an over-long input.

`Signup` binds, hashes through `auth.HashPassword`, calls `Create` with `verified=false` and a nil verification source, then calls `SendVerificationEmail`. Map `user.ErrEmailTaken` through `RespondError` to 409. A mailer failure is logged and still returns 201: the account exists and the user can resend, so failing the whole signup on a transient mail outage would be worse. Respond 201 with `{"user_id": ...}`.

`Login` binds, looks the account up with `GetByEmailCI`, and calls `auth.ComparePassword`. On a missing account, call `ComparePassword` against a fixed dummy bcrypt hash before returning so the failure path performs the same work either way. RESEARCH.md's Security Domain requires unknown-account and wrong-password to be indistinguishable; returning early on a miss would make the two cases separable by response time even though the bodies match. Both paths return `user.ErrInvalidCredentials` through `RespondError`. When credentials are good but `EmailVerified` is false, return `user.ErrEmailNotVerified`, which maps to 403 and which the client uses to route to the waiting screen. Otherwise issue an access token and a refresh token and respond 200 with the `AuthResult` shape.

`Register` attaches the limits from plan 01-06: `POST /auth/signup` wrapped in `RateLimit(LimitConfig{Requests: 3, Window: time.Minute, KeyFunc: KeyByIP})` and `POST /auth/login` wrapped in `RateLimit(LimitConfig{Requests: 5, Window: time.Minute, KeyFunc: KeyByIPAndField("email")})`.

Write the tests against `newTestRouter` with the in-memory fakes. The indistinguishability test must compare the full response body and status of the unknown-account and wrong-password cases for byte equality.

<task type="auto" tdd="true">
  <name>Task 2: Refresh and logout handlers</name>
  <files>internal/httpapi/auth.go, internal/httpapi/auth_test.go</files>
  <behavior>
    - POST /v1/auth/refresh with a valid refresh token returns 200 with a new access and refresh token pair
    - The refresh token returned differs from the one presented
    - Presenting the same refresh token a second time returns 401 token_invalid
    - An expired refresh token returns 401 token_expired
    - POST /v1/auth/logout revokes the presented token, and a later refresh with it returns 401
    - Logout with an already-invalid token returns 204 rather than an error
  </behavior>
  <read_first>
    - internal/httpapi/auth.go (written in Task 1 - extend the same handler struct and Register method)
    - .planning/phases/01-foundation-accounts/01-06-SUMMARY.md (RefreshService.Redeem and Revoke signatures)
    - lib/session/store.ts (plan 01-05 - the client persists both returned tokens and depends on rotation)
  </read_first>
  <action>
Add `Refresh` and `Logout` to `AuthHandler` and register `POST /auth/refresh` and `POST /auth/logout` in the existing `Register` method. Neither route sits behind `RequireAuth`: the whole point of refresh is that the access token has already expired, and logout must work from the same state.

`Refresh` binds `{ RefreshToken string \`json:"refresh_token" binding:"required"\` }`, calls `RefreshService.Redeem`, which validates and rotates in one step, then issues a fresh access token for the returned user ID and responds 200 with `access_token`, `refresh_token`, and `expires_in`. Propagate `user.ErrTokenExpired` and `user.ErrTokenInvalid` through `RespondError` unchanged, because the mobile client branches on exactly those two codes: `token_expired` drives its single-flight refresh retry, while `token_invalid` drives a sign-out.

The response must always carry the rotated refresh token. The client persists both values on every refresh, and omitting the new refresh token would leave the device holding a token the server has already revoked, which would present as a spurious forced logout on the next launch.

`Logout` binds the same body, calls `RefreshService.Revoke`, and responds 204. A token that is already missing or revoked still returns 204: the client calls logout on a best-effort basis and must not be trapped in a signed-in shell by a failure here.

Extend `auth_test.go` with the six behaviors. The rotation test asserts both that the second redemption fails and that the returned token differs from the one presented, since either check alone would pass a broken implementation.
  </action>

    - Logout returns 204 for an unknown token
    - Neither route is wrapped in `RequireAuth`

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| public internet -> credential endpoints | Unauthenticated traffic reaches password verification |
| refresh token -> new session | A bearer secret is exchanged for fresh access |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-01-PWD-01 | Spoofing | credential stuffing against `POST /v1/auth/login` | high | mitigate | 5 requests per minute keyed by client IP and by the targeted email, attached in `Register` |
| T-01-PWD-02 | Information Disclosure | account enumeration by response difference or timing | high | mitigate | Identical body and status for unknown-account and wrong-password, asserted byte-equal in test; the missing-account path still runs a bcrypt comparison against a fixed dummy hash so the timing profile matches |
| T-01-PWD-03 | Spoofing | account takeover through an unverified address | high | mitigate | Login returns 403 `email_not_verified` rather than a session when `email_verified` is false, satisfying D-04 at the API boundary rather than only in the UI |
| T-01-PWD-04 | Elevation of Privilege | refresh token replay | high | mitigate | `Redeem` rotates transactionally; the second use of a token fails, asserted in test |
| T-01-PWD-05 | Denial of Service | signup flood creating accounts and mail volume | medium | mitigate | 3 requests per minute per IP on signup; a mailer failure does not roll back the account so the limiter, not the mail provider, is the throttle |
| T-01-PWD-06 | Tampering | oversized password as a bcrypt CPU amplifier | medium | mitigate | `binding:"required,min=8,max=72"` rejects before hashing |
| T-01-PWD-07 | Information Disclosure | verification email sent to an address the requester does not control | low | accept | Inherent to any email verification flow; the token is single-use and expiring, and no session is granted until it is redeemed |
</threat_model>
