Create `lib/api/types.ts` declaring the wire contract that the Go backend in plans 01-08 through 01-11 implements. Every type below is the single source of truth shared by all mobile screens.

`ApiUser`: `{ id: string; email: string; name: string | null; username: string | null; bio: string | null; avatar_url: string | null; email_verified: boolean; onboarding_complete: boolean }`.
`SessionTokens`: `{ access_token: string; refresh_token: string; expires_in: number }`.
`AuthResult`: `SessionTokens & { user: ApiUser; is_new_user?: boolean }`.
`SignupResult`: `{ user_id: string }`.
`UsernameSuggestion`: `{ username: string; alternates: string[] }`.
`UsernameAvailability`: `{ available: boolean; alternates: string[] }`.
`AvatarUploadTicket`: `{ upload_url: string; public_url: string; expires_in: number }`.
`ApiErrorBody`: `{ error: string; message?: string; suggestions?: string[] }`.

Declare the error code union `ApiErrorCode = 'invalid_credentials' | 'email_taken' | 'username_taken' | 'email_not_verified' | 'token_invalid' | 'token_expired' | 'token_consumed' | 'rate_limited' | 'validation_failed' | 'network_unavailable' | 'server_error'`.

Create `lib/api/client.ts` exporting `class ApiError extends Error` carrying `status: number`, `code: ApiErrorCode`, and `suggestions?: string[]`, plus a `userMessage` getter that returns UI-SPEC's Copywriting Contract strings verbatim for the cases the contract declares: `network_unavailable` returns "Couldn't connect. Check your connection and try again." and `email_taken` returns "That email's already registered. Log in instead." Any other code returns a generic fallback that the calling screen is expected to override with screen-specific copy.

Export `api` with methods `get<T>(path, opts?)`, `post<T>(path, body, opts?)`, and `patch<T>(path, body, opts?)`. Base URL comes from `process.env.EXPO_PUBLIC_API_BASE_URL` with a development default of `http://localhost:8080`; add `EXPO_PUBLIC_API_BASE_URL` to the Expo `extra` config if a non-default is needed. All paths are prefixed with `/v1`.

Behavior each request follows: read the current access token from the session store's in-memory accessor and set `Authorization: Bearer <token>` when present and when `opts.auth` is not explicitly false; set `Content-Type: application/json`; wrap the `fetch` in a try/catch that converts a thrown network error into an `ApiError` with code `network_unavailable`; parse a non-2xx JSON body into `ApiError` using its `error` field as the code.

On a 401 with code `token_expired` (and only when `opts.retry` is not already true) the client calls the session store's `refreshSession()` and retries the original request exactly once with the new access token. Guard this with a module-level `refreshPromise: Promise<void> | null` so several requests failing concurrently await one shared refresh rather than each firing its own, which would rotate the refresh token several times in parallel and invalidate the survivors. Clear `refreshPromise` in a `finally`. If the refresh itself fails, the client calls the session store's `signOut()` and rethrows the original error.

The client never reads or writes SecureStore directly. It reaches persistence only through the two accessors the session store exports in Task 2, so there is exactly one module that touches the keychain.

  <files>lib/session/store.ts</files>

    - lib/api/types.ts (written in Task 1 - ApiUser and SessionTokens)

  <action>
Create `lib/session/store.ts` exporting `SessionStatus = 'loading' | 'unauthenticated' | 'authenticated'`, a `SessionProvider` component, and a `useSession()` hook.

Persistence uses `expo-secure-store` under two keys, `rndmroll.access_token` and `rndmroll.refresh_token`, written with `setItemAsync` and `keychainAccessible: SecureStore.WHEN_UNLOCKED_THIS_DEVICE_ONLY`. RESEARCH.md's Don't Hand-Roll table is explicit that plain `AsyncStorage` is unencrypted and that SecureStore wrapping the iOS Keychain and Android Keystore is the platform-sanctioned place for credentials, so no token value may be written anywhere else, including React state that survives a reload or any logging call.

`useSession()` returns `{ status, user, signIn, signOut, refreshSession, reloadUser }`.

`signIn(result: AuthResult)` writes both tokens to SecureStore, sets the in-memory access token, sets `user` from `result.user`, and moves `status` to `'authenticated'`.

`signOut()` calls `POST /v1/auth/logout` with the stored refresh token on a best-effort basis (swallowing any error, since a network failure must not trap the user in a signed-in shell), deletes both SecureStore keys, clears the in-memory access token and user, and sets `status` to `'unauthenticated'`.

`refreshSession()` reads the persisted refresh token and calls `POST /v1/auth/refresh` with `{ refresh_token }` and `auth: false`. On success it persists the rotated pair the server returns. The server rotates on every refresh, so failing to persist the new refresh token would invalidate the session on the next launch. On failure it calls `signOut()` and rethrows.

`reloadUser()` calls `GET /v1/me` and replaces `user`, so the name, username, and photo steps of the onboarding sequence can refresh `onboarding_complete` after each `PATCH /v1/me`.

The provider runs a `restore()` effect exactly once on mount: read the refresh token from SecureStore; when absent, set `status` to `'unauthenticated'`; when present, call `refreshSession()` then `reloadUser()`, setting `'authenticated'` on success and `'unauthenticated'` on failure. This effect is the relaunch half of ACCT-01's stay-logged-in chain.

Also export `getAccessToken()` and `setAccessToken()` module-level accessors that `lib/api/client.ts` imports, plus `registerSessionHandlers({ refreshSession, signOut })` which the provider calls on mount so the client can drive refresh and sign-out without importing React context.
  </action>

Route gating uses `Stack.Protected` with boolean guards, the officially documented Expo Router API cited in RESEARCH.md Pattern 3. Three guards:
`<Stack.Protected guard={status === 'authenticated' && user?.onboarding_complete === true}>` wraps `<Stack.Screen name="(app)" />`.
`<Stack.Protected guard={status !== 'authenticated' || user?.onboarding_complete === false}>` wraps `<Stack.Screen name="(auth)" />`.
The second guard is what implements D-05 step 6. A user who has verified their email holds a real session but has not yet set a name and username, so `onboarding_complete` is false and they stay inside `(auth)` for the remaining steps rather than landing in the app half-configured. `onboarding_complete` is computed server-side by `User.OnboardingComplete()` from plan 01-03, so the client never re-derives the rule.

This resume rule means a user who closes the app mid-onboarding returns to the step they left rather than restarting.

`app/(app)/_layout.tsx` renders a `Stack` with `contentStyle: { backgroundColor: color.dominant }` declaring the `profile` route group. <threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| app process -> OS keychain | Long-lived refresh token crosses into device storage |
| app -> backend over HTTPS | Bearer tokens travel on every request |
| device owner -> app | A device in someone else's hands must not expose a session |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-01-CLI-01 | Information Disclosure | on-device token storage | high | mitigate | `expo-secure-store` with `WHEN_UNLOCKED_THIS_DEVICE_ONLY`; `lib/session/store.ts` is the only module permitted to import it, enforced by the Task 2 verify gate, so no screen can copy a token into unencrypted storage |
| T-01-CLI-02 | Elevation of Privilege | concurrent refresh racing the rotation | high | mitigate | Module-level single-flight `refreshPromise` in `lib/api/client.ts`; without it, parallel refreshes would rotate the server-side token repeatedly and strand the survivors, presenting as spurious forced logouts |
| T-01-CLI-03 | Spoofing | a half-onboarded session reaching app screens | medium | mitigate | The `(app)` guard requires server-computed `onboarding_complete`, not just `status === 'authenticated'` |
| T-01-CLI-04 | Information Disclosure | tokens written to a log or crash report | high | mitigate | No `console.log` of token values anywhere in `lib/session` or `lib/api`; `ApiError` carries a code and status, never the request Authorization header |
| T-01-CLI-05 | Tampering | plaintext HTTP in production | high | mitigate | `EXPO_PUBLIC_API_BASE_URL` defaults to `http://localhost:8080` only for local development; the release build must point at an HTTPS origin, checked at the plan 01-15 UAT checkpoint |
| T-01-CLI-06 | Denial of Service | refresh failure loop on a revoked token | medium | mitigate | A failed refresh calls `signOut()` once and rethrows rather than retrying, so a revoked session ends at the login screen instead of spinning |
</threat_model>
