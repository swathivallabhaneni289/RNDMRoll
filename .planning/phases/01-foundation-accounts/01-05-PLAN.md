<objective>
Build the client-side session backbone: SecureStore persistence, the typed API client with single-flight refresh on 401, the non-credential intro flag, and the three Expo Router layouts that gate the app behind an authenticated, onboarded session.

Purpose: ACCT-01's "stays logged in across app sessions" is not a storage concern alone. It is a chain: SecureStore write, root-layout read on relaunch, refresh call, route decision. This plan owns that entire chain so no fragment of it is orphaned between plans.

D-05 (revised 2026-09-17) changes what sits at the front and the back of that chain. The front gains a four-screen pre-signup marketing sequence, which needs a durable, non-credential record of whether it has already been shown so a returning unauthenticated user is not marched through the pitch again after logging out. The back collapses: the separate name, username, and photo steps become one create-profile screen, so the old per-step resume decision tree reduces to a single destination.

Output: `lib/session/`, `lib/api/`, `lib/onboarding/intro-seen.ts`, and the `app/` layout tree.
</objective>

Create `lib/api/client.ts` exporting `class ApiError extends Error` carrying `status: number`, `code: ApiErrorCode`, and `suggestions?: string[]`, plus a `userMessage` getter that returns UI-SPEC's Copywriting Contract strings verbatim for the cases the contract declares: `network_unavailable` returns "Couldn't connect. Export `api` with methods `get<T>(path, opts?)`, `post<T>(path, body, opts?)`, and `patch<T>(path, body, opts?)`. Base URL comes from `process.env.EXPO_PUBLIC_API_BASE_URL` with a development default of `http://localhost:8080`; add `EXPO_PUBLIC_API_BASE_URL` to the Expo `extra` config if a non-default is needed. All paths are prefixed with `/v1`.

Behavior each request follows: read the current access token from the session store's in-memory accessor and set `Authorization: Bearer <token>` when present and when `opts.auth` is not explicitly false; set `Content-Type: application/json`; wrap the `fetch` in a try/catch that converts a thrown network error into an `ApiError` with code `network_unavailable`; parse a non-2xx JSON body into `ApiError` using its `error` field as the code.

On a 401 with code `token_expired` (and only when `opts.retry` is not already true) the client calls the session store's `refreshSession()` and retries the original request exactly once with the new access token. Guard this with a module-level `refreshPromise: Promise<void> | null` so several requests failing concurrently await one shared refresh rather than each firing its own, which would rotate the refresh token several times in parallel and invalidate the survivors. Clear `refreshPromise` in a `finally`. If the refresh itself fails, the client calls the session store's `signOut()` and rethrows the original error.

The client never reads or writes SecureStore directly. It reaches persistence only through the two accessors the session store exports in Task 2, so there is exactly one module that touches the keychain.

  <action>
Create `lib/session/store.ts` exporting `SessionStatus = 'loading' | 'unauthenticated' | 'authenticated'`, a `SessionProvider` component, and a `useSession()` hook.

Persistence uses `expo-secure-store` under two keys, `rndmroll.access_token` and `rndmroll.refresh_token`, written with `setItemAsync` and `keychainAccessible: SecureStore.WHEN_UNLOCKED_THIS_DEVICE_ONLY`. RESEARCH.md's Don't Hand-Roll table is explicit that plain `AsyncStorage` is unencrypted and that SecureStore wrapping the iOS Keychain and Android Keystore is the platform-sanctioned place for credentials, so no token value may be written anywhere else, including React state that survives a reload or any logging call.

`useSession()` returns `{ status, user, signIn, signOut, refreshSession, reloadUser }`.

`signIn(result: AuthResult)` writes both tokens to SecureStore, sets the in-memory access token, sets `user` from `result.user`, and moves `status` to `'authenticated'`.

`signOut()` calls `POST /v1/auth/logout` with the stored refresh token on a best-effort basis (swallowing any error, since a network failure must not trap the user in a signed-in shell), deletes both SecureStore keys, clears the in-memory access token and user, and sets `status` to `'unauthenticated'`.

`refreshSession()` reads the persisted refresh token and calls `POST /v1/auth/refresh` with `{ refresh_token }` and `auth: false`. On success it persists the rotated pair the server returns. The server rotates on every refresh, so failing to persist the new refresh token would invalidate the session on the next launch. On failure it calls `signOut()` and rethrows.

`reloadUser()` calls `GET /v1/me` and replaces `user`, so the create-profile screen can refresh `onboarding_complete` after its `PATCH /v1/me`.

The provider runs a `restore()` effect exactly once on mount: read the refresh token from SecureStore; when absent, set `status` to `'unauthenticated'`; when present, call `refreshSession()` then `reloadUser()`, setting `'authenticated'` on success and `'unauthenticated'` on failure. This effect is the relaunch half of ACCT-01's stay-logged-in chain.

Also export `getAccessToken()` and `setAccessToken()` module-level accessors that `lib/api/client.ts` imports, plus `registerSessionHandlers({ refreshSession, signOut })` which the provider calls on mount so the client can drive refresh and sign-out without importing React context.
  </action>

| Boundary | Description |
|----------|-------------|
| app process -> OS keychain | Long-lived refresh token crosses into device storage |
| app process -> unencrypted device storage | The non-credential intro flag crosses into AsyncStorage |

| device owner -> app | A device in someone else's hands must not expose a session |
