`internal/auth/password.go` in package `auth` exports `HashPassword(plain string) (string, error)` and `ComparePassword(hash, plain string) error`.

`HashPassword` calls `bcrypt.GenerateFromPassword([]byte(plain), bcrypt.DefaultCost)`. Before hashing, reject any input whose byte length exceeds 72 with a named `ErrPasswordTooLong`. RESEARCH.md Pitfall 1 is explicit that 72 is a hard algorithmic ceiling measured in bytes rather than characters, so a multi-byte password hits it sooner than its visible length suggests, and that the correct response is a clear validation error rather than a pre-hash workaround. Do not apply SHA-256 or any other digest before bcrypt.

`ComparePassword` calls `bcrypt.CompareHashAndPassword` and maps any mismatch to `user.ErrInvalidCredentials`. It returns that same error for an empty or malformed stored hash, which is the social-only account case, so a login attempt against an account that has no password is indistinguishable from a wrong password.

`internal/auth/jwt.go` exports `IssueAccessToken(userID uuid.UUID, secret []byte, ttl time.Duration) (string, error)` and `ParseAccessToken(token string, secret []byte) (uuid.UUID, error)`.

`IssueAccessToken` builds `jwt.RegisteredClaims` with `Subject` set to the user ID string, `ExpiresAt` at now plus `ttl`, `IssuedAt` at now, and `NotBefore` at now, signs with `jwt.SigningMethodHS256` through `golang-jwt/jwt/v5`, and returns the signed string.

`ParseAccessToken` calls `jwt.ParseWithClaims` with `jwt.WithValidMethods([]string{"HS256"})` and a keyfunc that additionally asserts the token's method is `*jwt.SigningMethodHMAC` before returning the secret. Passing the expected method explicitly rather than relying on library defaults is the mitigation RESEARCH.md's Security Domain names for algorithm-confusion attacks. Map a parse or validation failure to `user.ErrTokenInvalid`, and a specifically expired token to `user.ErrTokenExpired`, since the mobile client in plan 01-05 branches on the expired code to trigger its single-flight refresh.

Write both test files covering the seven behaviors listed above. The `alg: none` test must construct the token by hand, since the library will not sign one for you: build the header and claims segments, base64url-encode them, and join with an empty signature.

`internal/auth/refresh.go` exports `type RefreshService struct` holding a `user.RefreshTokenRepository` and a TTL, constructed by `NewRefreshService(repo user.RefreshTokenRepository, ttl time.Duration) *RefreshService`.

`Issue(ctx, userID uuid.UUID, userAgent *string) (string, error)` reads 32 bytes from `crypto/rand`, encodes them with `base64.RawURLEncoding` as the opaque token returned to the client, computes `sha256.Sum256` over the raw bytes, and stores only that digest through the repository's `Insert`. RESEARCH.md's Security Domain requires refresh tokens be stored hashed rather than plaintext so that a database disclosure does not hand over live sessions.

`Redeem(ctx, token string, userAgent *string) (userID uuid.UUID, newToken string, err error)` decodes and hashes the presented token, calls `GetActiveByHash`, propagates `ErrTokenExpired` and `ErrTokenInvalid` unchanged, then generates a fresh token and calls the repository's transactional `Rotate` to revoke the presented row and insert the replacement atomically. Returning a new token on every redemption is the replay-window mitigation RESEARCH.md prescribes: a stolen token is useful only until the legitimate client next refreshes, at which point the thief's copy is already revoked.

`Revoke(ctx, token string) error` hashes and calls `RevokeByHash`, tolerating a miss so that signing out with an already-invalid token still succeeds. `RevokeAll(ctx, userID uuid.UUID) error` delegates to `RevokeAllForUser`.

The test file uses an in-memory fake implementing `user.RefreshTokenRepository` rather than a database, so this suite runs with no `TEST_DATABASE_URL`. Place that fake in `refresh_test.go`; plan 01-03's Postgres suite already covers the real implementation's transactional behavior.
  </action>

`internal/middleware/auth.go` exports `RequireAuth(secret []byte) gin.HandlerFunc` and `SubjectFromContext(c *gin.Context) (uuid.UUID, error)`.

`RequireAuth` reads the `Authorization` header, requires the `Bearer ` prefix, calls `auth.ParseAccessToken`, and on success stores the subject under the context key `authSubject` using a package-private typed key. On any failure it aborts with 401 and the body `{"error":"token_expired"}` for an expired token or `{"error":"token_invalid"}` otherwise, matching the codes the mobile client branches on.

`SubjectFromContext` returns an error rather than a zero value when the key is absent. This is deliberate: PATTERNS.md's access-control rule requires `GET` and `PATCH /me` to derive the target user exclusively from the token subject, and a silent zero UUID would turn a missing-middleware wiring bug into a data-exposure bug.

`internal/middleware/ratelimit.go` exports `type LimitConfig struct { Requests int; Window time.Duration; KeyFunc func(*gin.Context) string }` and `RateLimit(cfg LimitConfig) gin.HandlerFunc`. Implement it over `golang.org/x/time/rate` with one `*rate.Limiter` per key held in a mutex-guarded map, entries evicted after ten idle windows so the map cannot grow without bound. On rejection abort with 429 and the body `{"error":"rate_limited"}`. Export three ready-made key functions: `KeyByIP` using `c.ClientIP()`, `KeyByIPAndField(field string)` which combines the client IP with a lowercased JSON body field so login throttling applies per account as well as per source, and `KeyBySubject` using the authenticated subject for post-login routes.

The wave 4 handler plans attach these limits: `POST /v1/auth/login` at 5 per minute keyed by IP and by the `email` field, `POST /v1/auth/signup` at 3 per minute by IP, `POST /v1/auth/verify-email/resend` at 1 per 30 seconds by IP and `email` field (matching UI-SPEC's 30-second resend cooldown so the client countdown and the server limit agree), and `GET /v1/usernames/available` at 20 per minute by subject. RESEARCH.md's Security Domain names rate limiting as the standard control for both credential stuffing and username enumeration, and this phase's ASVS level 1 block-on-high setting means neither can be dispositioned as accepted.

`internal/httpapi/errors.go` exports `Respond(c *gin.Context, status int, body any)` and `RespondError(c *gin.Context, err error)`. `RespondError` maps with `errors.Is`: `user.ErrInvalidCredentials` to 401 `invalid_credentials`; `user.ErrEmailTaken` to 409 `email_taken`; `user.ErrUsernameTaken` to 409 `username_taken`; `user.ErrEmailNotVerified` to 403 `email_not_verified`; `user.ErrNotFound` to 404 `not_found`; `user.ErrTokenInvalid` to 401 `token_invalid`; `user.ErrTokenExpired` to 401 `token_expired`; `user.ErrTokenConsumed` to 409 `token_consumed`; `user.ErrSubjectLinkedToOtherAccount` to 409 `subject_linked`; anything else to 500 `server_error` with the underlying message logged rather than returned. Every code string here appears in the `ApiErrorCode` union in `lib/api/types.ts`, so client and server agree without a translation layer. Also export `RespondValidationError(c, err)` producing 400 `validation_failed`, used by handlers after a failed `ShouldBindJSON`.

`internal/httpapi/testsupport_test.go` in package `httpapi` provides the shared harness the wave 4 plans build on: `newTestRouter(t *testing.T, deps TestDeps) *gin.Engine` returning a `gin.New()` with recovery attached, and in-memory fakes `fakeUserRepo`, `fakeRefreshRepo`, `fakeVerificationRepo`, and `fakeMailer` implementing the plan 01-03 interfaces plus the mailer interface plan 01-09 declares. Because every wave 4 handler mounts itself on a fresh engine inside its own test, no handler test depends on `cmd/api/main.go` existing, which is what keeps those five plans in one wave.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| public internet -> auth routes | Unauthenticated, unthrottled traffic reaches credential checks |
| bearer token -> handler identity | Everything downstream trusts the subject this layer extracts |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-01-AUTH-01 | Spoofing | credential stuffing and brute force against `POST /v1/auth/login` | high | mitigate | `RateLimit` with `KeyByIPAndField("email")` at 5 per minute, throttling per source and per targeted account; paired with the single `ErrInvalidCredentials` result so failures carry no signal |
| T-01-AUTH-02 | Tampering | JWT algorithm confusion, including `alg: none` | high | mitigate | `ParseAccessToken` passes `jwt.WithValidMethods([]string{"HS256"})` and re-asserts `*jwt.SigningMethodHMAC` inside the keyfunc; a hand-built alg-none token is a required failing test case |
| T-01-AUTH-03 | Elevation of Privilege | handler reading a client-supplied user ID | high | mitigate | `SubjectFromContext` returns an error when the middleware did not run, so no handler can fall back to a zero UUID; PATTERNS.md's `/me` rule is enforced structurally |
| T-01-AUTH-04 | Information Disclosure | account enumeration through login or availability responses | high | mitigate | One `ErrInvalidCredentials` for both unknown-account and wrong-password; availability endpoint throttled at 20 per minute by subject in plan 01-11 |
| T-01-AUTH-05 | Elevation of Privilege | refresh token replay | high | mitigate | `RefreshService.Redeem` rotates on every use through the repository's transactional `Rotate`, and stores only SHA-256 digests |
| T-01-AUTH-06 | Information Disclosure | internal error text reaching the client | medium | mitigate | `RespondError` returns a fixed `server_error` code for unmapped errors and logs the underlying message server-side |
| T-01-AUTH-07 | Denial of Service | unbounded limiter map growth from rotating source addresses | medium | mitigate | Limiter entries evicted after ten idle windows under a mutex |

| T-01-AUTH-09 | Repudiation | no record of failed authentication attempts | low | accept | Structured request logging lands in plan 01-13; a dedicated security audit trail is beyond ASVS level 1 for a private friend-group app |
