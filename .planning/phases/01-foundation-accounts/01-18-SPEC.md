Try again in 52 minutes.'

Screen reader label 'Send a new code, available in 40 seconds' updates every 10 seconds, not every second. RESEND: tap sends, button spinner, then a confirmation line under the buttons 'New code sent. Your earlier code no longer works.' and the countdown restarts from the server's number. App backgrounded: state kept; iOS may offer the code above the keyboard when it arrives (Apple documents that for SMS only, research section 2), so typing and pasting must always work. - back_behavior: Back (and Change email) return to /email with the address kept and the code cleared. The verified token is kept in memory.
- notes: No 'Verified' interstitial: the old 900 ms success state is dropped (one question, one step). Success returns {signup_token}, an opaque, memory-only proof that this address was verified, alive 30 minutes from its last use. Test mode (MAIL_DRIVER=log): the code is printed in the API log, ~/.local/share/rndmroll-api/api.log, in the mail: block; the screen has no dev shortcut that fills it, so the real path is what gets tested. ## Apple and Google path
Apple and Google both start on choose-method and share one rule: a provider identity RNDMRoll already knows signs straight in (existing behavior, no new screens). A provider identity it does not know creates NO account yet. The server verifies the provider token as it does today, then answers with a pending sign-up (signup_token, the provider's email, a suggested name) instead of a session. The app then shows only four screens: Birthday, Name, Username, Agree, with step labels 01 / 04 to 04 / 04. Skipped because the provider already proved it: Email, Code, Password. Still required: Birthday (the age rule applies to everyone), Username (the provider has none), Agree. Name is shown, prefilled from the provider (Google sends it every time; Apple only on the first authorization, so the app keeps it in memory the moment it arrives, as lib/auth/social.ts already does), and stays editable. The final Create account call links the provider subject, marks the email verified through the provider, and creates the user in one step, so a person under 13 leaves nothing behind. Test mode: Apple uses the simulator's Apple ID; Google stays a stand-in until the developer sets up real credentials at the end, and no screen here needs a real credential. Back from Birthday returns to choose-method (the pending token is dropped, the user taps the provider again). If the provider email matches an existing password account the server keeps today's link-to-existing-account rule (oauth.go) and signs that account in, so it never reaches Birthday.

## Log-in path
The Log in link lives in three places and always opens one dedicated screen, app/(auth)/login.tsx (email and password together): a line 'Already have an account?' plus the link 'Log in' under the buttons on choose-method, and the link 'Log in instead' on the Email and Code screens. The login screen has 'Sign up instead' to go the other way. Providers do not use that screen: a person who signed up with Apple or Google taps the same provider button on choose-method. Success calls signIn(result) and the root guard opens the Profile (or the catch-up screens if the account is not complete). A login for an unverified old account sends a code and opens the Code screen (the link screen it used to open is deleted). Gap to record, not to build now: there is no 'Forgot password?' because no reset exists in the API; a forgotten password locks the account out until one is built, and it should reuse the same 6-digit code mechanism and Code screen when it is, which is also the moment the domain and universal links matter again.

## Resume and abandon
What survives a relaunch, stated plainly. Email path: nothing. The draft (email, token, password, birthday, name, username) is in memory on purpose (lib/onboarding/draft.ts says so), only lib/session/store.ts may touch SecureStore, and a password or birthday written to disk would be worse than retyping. Welcome shows first on every signed-out launch, and this spec does not change that, because resuming mid-sign-up would mean touching app/index.tsx routing, the most fragile area in the repo. So killing the app mid-sign-up means: Welcome, Get started, Continue with Email, and the same address again. If another send is still inside its 60 second cooldown the server does not email again and the earlier code still works (the Code screen shows the remaining seconds); after that a new code is sent and the earlier one dies. A code emailed but never used simply expires after 10 minutes. Backgrounding without a kill keeps everything; the token's 30 minute timeout is first noticed on the Birthday screen as 'This sign-up timed out. Start again.' with the address filled. The code step, where people leave to read Mail, is the most likely place to be backgrounded, and it survives that. Provider path: same rule, restart at Welcome; Apple will not repeat the name after its first authorization, so a relaunched Apple sign-up asks for the name by typing. Catch-up for an account that already exists but is not complete (old half-onboarded rows, or all old rows if decision 2 says so): the (auth) layout's existing redirect for a signed-in incomplete user stops pointing at the deleted /profile-setup and points at the first missing step among Birthday, Name, Username, Agree, shown with the same screens in signed-in mode (no email, code or password, and the final call is an authenticated update instead of create). That redirect is in a hazard file, so it needs a cold launch of the dev client. The live rndmroll_dev database holds real test accounts: the migration must only add nullable columns and must not delete rows; count the unverified and the half-onboarded rows read-only before deciding anything about them (I did not and cannot query it).

## Age rules
Minimum age 13, the same everywhere for now. Stored: the birthday as a date on the users row once the account exists, plus terms_version and terms_accepted_at. Never stored: anything about a rejected attempt (no email, no date, no flag), on the server or the device. The birthday is never returned by the API (kept out of apiUser and profileBody), never shown in the app, never editable in Edit profile (editing it would be a way around the gate), and must stay out of logs. Under 13: the Birthday screen shows 'RNDMRoll is for ages 13 and up.' and 'We can't make an account for you. Nothing you entered was saved.' with 'Start over'; the server drops the pending sign-up; on the provider path no account was ever created. The server decides age from its own clock; the client check only saves a round trip. Honest limits to tell the developer: the age is self-reported, so a person can press Start over and type another date, or use another email or device; RNDMRoll does no ID check and, by design here, remembers nothing about a refused attempt; Instagram's own block has the same limit. Not a legal ruling: 13 is the common floor in the research (Instagram says higher in some countries), and some regions set the age of digital consent higher, so the developer should confirm the launch regions before release. Optional hardening if wanted later, not recommended by default: a 24 hour lock stored on the device, which stores a flag about a child and is bypassed by reinstalling.

## Agree screen proposal
The repo has no Terms or Privacy documents and no domain to host them, and I will not write legal text. Proposal for now: build the Agree screen as a real, final step, but as a plain statement of what the app keeps (five short lines, each true of the code today, plus 'Nobody else sees your email or your birthday.'), with the button 'Create account' (an existing approved string) instead of 'I agree', because nothing legal exists to agree to. Record terms_version 'none' and a timestamp, so the flow, the database column and the completeness rule are already in place. When the developer supplies documents, switch the same screen to the agree variant: heading 'Agree to the terms', body 'By tapping I agree you accept the Terms and the Privacy Policy.', two link rows 'Terms' and 'Privacy Policy' that open in-app text screens, button 'I agree', and a real terms_version so a later revision can ask again. What the developer must supply: the Terms text and the Privacy Policy text (written or reviewed by someone qualified, matching what the app really does, including the 13 age floor), and where they live. Bundled as in-app screens they need no domain; the App Store listing will still need a public privacy URL, which is covered by the existing launch gate (custom domain). Recommendation: ship the 'What RNDMRoll keeps' version in test mode, get the two documents written before the launch gate, then flip to the agree variant. The factual lines must be re-checked whenever the product changes (for example when friends can see more than name, username, bio and photo).
