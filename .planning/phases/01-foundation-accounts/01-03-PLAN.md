Write `migrations/0001_init.up.sql` creating three tables.

`users`: `id uuid primary key default gen_random_uuid()`, `email text not null`, `password_hash text` (nullable, social-only accounts have none), `name text`, `username text`, `bio text`, `avatar_url text`, `email_verified boolean not null default false`, `email_verified_via text check (email_verified_via in ('password_flow','apple','google'))`, `apple_subject text`, `google_subject text`, `created_at timestamptz not null default now()`, `updated_at timestamptz not null default now()`.

The `email_verified_via` column resolves RESEARCH.md Open Question 1 along the recommendation the researcher gave: record how an email was verified so the onboarding router can skip the redundant verification-email step for Apple and Google signups, whose providers already verified the address. D-04's requirement that a user cannot use the app on an unverified email is satisfied either way, because `email_verified` still gates access; only the mechanism differs by signup path. Choosing this branch also avoids taking on Apple's private-relay sender-domain registration dependency, which sending a verification email to an `@privaterelay.appleid.com` address would require.

Indexes enforcing case-insensitive uniqueness per RESEARCH.md Pitfall 4 (a plain `UNIQUE` on the raw column would let `Swathi` and `swathi` coexist):
`create unique index users_email_lower_idx on users (lower(email));`
`create unique index users_username_lower_idx on users (lower(username)) where username is not null;`
`create unique index users_apple_subject_idx on users (apple_subject) where apple_subject is not null;`
`create unique index users_google_subject_idx on users (google_subject) where google_subject is not null;`
Add a `check (length(bio) <= 160)` constraint on `bio` and `check (username ~ '^[a-z0-9_]{3,20}$')` so the charset rule lives at the storage layer as well as the validator layer.

`email_verification_tokens`: `id uuid primary key default gen_random_uuid()`, `user_id uuid not null references users(id) on delete cascade`, `token_hash bytea not null unique`, `expires_at timestamptz not null`, `consumed_at timestamptz`, `created_at timestamptz not null default now()`, plus `create index email_verification_tokens_user_idx on email_verification_tokens (user_id);`. Storing only the hash and carrying an expiry plus a consumed marker is RESEARCH.md Pitfall 5's mitigation for indefinitely replayable verification links.

`refresh_tokens`: `id uuid primary key default gen_random_uuid()`, `user_id uuid not null references users(id) on delete cascade`, `token_hash bytea not null unique`, `expires_at timestamptz not null`, `revoked_at timestamptz`, `rotated_to uuid references refresh_tokens(id)`, `user_agent text`, `created_at timestamptz not null default now()`, plus `create index refresh_tokens_user_idx on refresh_tokens (user_id);`.

Add a `set_updated_at()` trigger function and a `users_set_updated_at` BEFORE UPDATE trigger so `updated_at` maintenance is not a per-query concern.

Write `migrations/0001_init.down.sql` dropping the trigger, the function, and all three tables in reverse dependency order.

Apply with `DATABASE_URL="postgres://localhost:5432/rndmroll_dev?sslmode=disable" make migrate-up`, then verify a full `migrate-down` / `migrate-up` round trip leaves no residue.

Create `internal/user/model.go` in package `user`.

`type User struct` with fields `ID uuid.UUID`, `Email string`, `PasswordHash *string`, `Name *string`, `Username *string`, `Bio *string`, `AvatarURL *string`, `EmailVerified bool`, `EmailVerifiedVia *VerificationSource`, `AppleSubject *string`, `GoogleSubject *string`, `CreatedAt time.Time`, `UpdatedAt time.Time`. Nullable columns are pointers so "not set yet" is distinguishable from "set to empty", which the onboarding router in plan 01-05 depends on.

`type VerificationSource string` with constants `VerifiedViaPasswordFlow = "password_flow"`, `VerifiedViaApple = "apple"`, `VerifiedViaGoogle = "google"`.

Add `func (u *User) OnboardingComplete() bool` returning true when `u.EmailVerified` is true and both `u.Name` and `u.Username` are non-nil and non-empty. This single method is the authority for the D-05 step-6 "land in the app" condition; the API exposes it and the mobile root layout routes on it.

Declare sentinel errors with `errors.New`: `ErrNotFound`, `ErrEmailTaken`, `ErrUsernameTaken`, `ErrInvalidCredentials`, `ErrEmailNotVerified`, `ErrTokenInvalid`, `ErrTokenExpired`, `ErrTokenConsumed`, `ErrSubjectLinkedToOtherAccount`. `ErrInvalidCredentials` is deliberately singular: RESEARCH.md's Security Domain requires login to return the same failure for "no such user" and "wrong password" so the endpoint cannot be used to enumerate registered emails.

Create `internal/user/repository.go` declaring three interfaces, all methods taking `ctx context.Context` first.

`Repository`: `Create(ctx, email string, passwordHash *string, verified bool, via *VerificationSource) (*User, error)`; `GetByID(ctx, id uuid.UUID) (*User, error)`; `GetByEmailCI(ctx, email string) (*User, error)`; `GetByProviderSubject(ctx, provider VerificationSource, subject string) (*User, error)`; `LinkProviderSubject(ctx, id uuid.UUID, provider VerificationSource, subject string) error`; `UsernameTaken(ctx, username string) (bool, error)`; `MarkEmailVerified(ctx, id uuid.UUID, via VerificationSource) error`; `UpdateProfile(ctx, id uuid.UUID, p ProfilePatch) (*User, error)`.

`ProfilePatch struct { Name *string; Username *string; Bio *string; AvatarURL *string }` where a nil field means "leave unchanged".

`RefreshTokenRepository`: `Insert(ctx, userID uuid.UUID, tokenHash []byte, expiresAt time.Time, userAgent *string) (uuid.UUID, error)`; `GetActiveByHash(ctx, tokenHash []byte) (*RefreshToken, error)` returning `ErrTokenExpired` for an expired row and `ErrTokenInvalid` for a revoked or missing one; `Rotate(ctx, oldID uuid.UUID, newHash []byte, expiresAt time.Time) (uuid.UUID, error)` performing revoke-old-and-insert-new in one transaction; `RevokeByHash(ctx, tokenHash []byte) error`; `RevokeAllForUser(ctx, userID uuid.UUID) error`.

`RefreshToken struct { ID uuid.UUID; UserID uuid.UUID; ExpiresAt time.Time; RevokedAt *time.Time }`.

`EmailVerificationRepository`: `Insert(ctx, userID uuid.UUID, tokenHash []byte, expiresAt time.Time) error`; `ConsumeByHash(ctx, tokenHash []byte, now time.Time) (uuid.UUID, error)` returning the owning user ID and atomically setting `consumed_at`, returning `ErrTokenConsumed` / `ErrTokenExpired` / `ErrTokenInvalid` as appropriate; `DeleteForUser(ctx, userID uuid.UUID) error` used when a resend supersedes outstanding tokens.

Create `internal/store/postgres/db.go` exporting `NewPool(ctx context.Context, databaseURL string) (*pgxpool.Pool, error)` built on `github.com/jackc/pgx/v5/pgxpool`, with `MaxConns` 10 and a 5-second connect timeout, and a `Ping` on construction so a bad `DATABASE_URL` fails at startup rather than at first request.

Implement the three interfaces in `user_repo.go`, `refresh_token_repo.go`, and `email_verification_repo.go`, each as a struct holding `*pgxpool.Pool` with a `NewUserRepo(pool)` style constructor returning the `internal/user` interface type.

Every query uses pgx positional placeholders (`$1`, `$2`). No query is assembled with `fmt.Sprintf`, string concatenation, or a template: user-controlled values reach Postgres only as bound parameters. `UpdateProfile`'s partial update is expressed as a single statement using the `coalesce($n, column)` idiom rather than a dynamically built SET list, so even the partial-update path stays a fixed query string.

Map `*pgconn.PgError` with `Code == "23505"` to typed domain errors by inspecting `ConstraintName`: `users_email_lower_idx` yields `user.ErrEmailTaken`, `users_username_lower_idx` yields `user.ErrUsernameTaken`, `users_apple_subject_idx` or `users_google_subject_idx` yields `user.ErrSubjectLinkedToOtherAccount`. This insert-time mapping, not the pre-check in plan 01-11's availability endpoint, is the authoritative uniqueness decision, per RESEARCH.md Pitfall 4's race-window analysis. Map `pgx.ErrNoRows` to `user.ErrNotFound`.

Lookups by email use `where lower(email) = lower($1)` so the query can use `users_email_lower_idx`. `UsernameTaken` uses `where lower(username) = lower($1)`.

`Rotate` opens a transaction, sets `revoked_at = now()` and `rotated_to` on the old row, inserts the new row, and commits, so a crash mid-rotation cannot leave two simultaneously valid refresh tokens.

Write `internal/store/postgres/postgres_test.go` covering all six behaviors above. The suite reads `TEST_DATABASE_URL` and calls `t.Skip` with an explanatory message when it is unset, so `go test ./...` stays green on a machine without a test database. Each test truncates `users` (cascading to both token tables) in a `t.Cleanup`. Run the migrations against `TEST_DATABASE_URL` once in `TestMain` by shelling out to the `migrate` CLI.

## Trust Boundaries

|----------|-------------|
| handler -> repository | Untrusted request field values cross into SQL |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-01-DB-01 | Tampering | `internal/store/postgres/*.go` profile and auth queries | high | mitigate | pgx positional parameters exclusively; `UpdateProfile` uses `coalesce($n, column)` rather than a dynamically built SET list so no query string varies with input. Verify gate greps for SQL built by concatenation or `Sprintf`. |
| T-01-DB-02 | Spoofing | duplicate account via case-varied email | high | mitigate | `users_email_lower_idx` on `lower(email)`; insert-time 23505 mapping is authoritative, per RESEARCH.md Pitfall 4 |
| T-01-DB-03 | Elevation of Privilege | refresh token replay after rotation | high | mitigate | `Rotate` revokes old and inserts new in one transaction; `GetActiveByHash` rejects rows with a non-null `revoked_at` |
| T-01-DB-04 | Information Disclosure | verification token readable from a database dump | high | mitigate | `email_verification_tokens.token_hash` and `refresh_tokens.token_hash` are `bytea` hashes; no plaintext token column exists in the schema |
| T-01-DB-05 | Information Disclosure | login distinguishing unknown email from wrong password | high | mitigate | Only `ErrInvalidCredentials` is declared for the login path; no "user not found on login" error exists to leak |
| T-01-DB-06 | Denial of Service | oversized bio or username text | medium | mitigate | `check (length(bio) <= 160)` and `check (username ~ '^[a-z0-9_]{3,20}$')` at the storage layer, in addition to validator tags in plan 01-11 |
| T-01-DB-07 | Repudiation | no record of which device holds a session | low | accept | `refresh_tokens.user_agent` is captured but no audit log is built; out of scope at ASVS level 1 for a private friend-group app |
</threat_model>
