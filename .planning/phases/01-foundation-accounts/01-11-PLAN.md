  <action>
Create `internal/user/username.go` in package `user`.

`NormalizeUsername(displayName string) string` lowercases, replaces whitespace runs with a single underscore, strips every character outside `[a-z0-9_]`, collapses repeated underscores, trims leading and trailing underscores, and truncates to 20 characters. When the result is shorter than 3 characters it returns `user` as the base, so a name written entirely in a non-Latin script still yields a usable handle rather than an empty string.

`ValidateUsername(s string) error` enforces exactly the pattern the database check constraint enforces, `^[a-z0-9_]{3,20}$`, returning a descriptive error. Keeping the two in lockstep matters: a validator looser than the constraint turns a clear 400 into an opaque 500 at insert time.

`SuggestUsername(ctx, repo Repository, displayName string) (string, error)` normalizes, returns the base when `UsernameTaken` reports it free, and otherwise appends a random three or four digit suffix, retrying up to eight times before widening to a longer random suffix. The suffix is random rather than a sequential counter, as PATTERNS.md specifies, because an incrementing scheme both leaks roughly how many similar handles exist and degrades as a namespace fills.

`SuggestAlternates(ctx, repo Repository, base string, n int) ([]string, error)` returns `n` distinct free candidates, used to populate the taken-state suggestion chips the UI-SPEC username state machine describes.

Every function here is advisory. PATTERNS.md is explicit that the live check is a UX convenience and the authoritative rejection is the unique-index violation at insert time, which plan 01-03 already maps to `ErrUsernameTaken`. Nothing in this file may be treated as a guarantee that a save will succeed.

Tests use the in-memory repository fake and cover all seven behaviors, including asserting that two suggestions for the same taken base differ.
  </action>

Build an `aws-sdk-go-v2` S3 client with static credentials, the configured region, `BaseEndpoint` set to the configured endpoint, and path-style addressing enabled so the same code works against AWS S3, Cloudflare R2, and a local MinIO without branching. Generate the URL with `s3.NewPresignClient(client).PresignPutObject` at a 300 second expiry.

Allow only `image/jpeg`, `image/png`, and `image/webp`, and cap `contentLength` at 5 MiB, returning named errors for each rejection. Both constraints are bound into the presigned request itself, not merely checked in Go, so the storage provider enforces them even if the client ignores what it was handed.

Tests construct the store against a stub presigner seam and cover the five behaviors offline. Live upload against real credentials is exercised at plan 01-15's walkthrough; record that in the SUMMARY.

Every handler resolves its target user through `SubjectFromContext` and nothing else. PATTERNS.md states the rule plainly: `GET` and `PATCH /me` must derive the target user exclusively from the authenticated token's subject, never from a client-supplied identifier. There is no `:id` path parameter anywhere in this plan and no user ID field on any request DTO, so there is no route through which one account could address another. Write the ignored-body-ID test anyway, because the assertion documents the guarantee.

`GET /me` responds 200 with the `ApiUser` shape: `id`, `email`, `name`, `username`, `bio`, `avatar_url`, `email_verified`, and `onboarding_complete` computed by `User.OnboardingComplete()` from plan 01-03. The client's route guard reads that boolean, so computing it server-side keeps the rule in one place.

`PATCH /me` binds `UpdateProfileRequest{ Name *string \`json:"name" binding:"omitempty,min=1,max=50"\`; Username *string \`json:"username" binding:"omitempty,min=3,max=20"\`; Bio *string \`json:"bio" binding:"omitempty,max=160"\`; AvatarURL *string \`json:"avatar_url" binding:"omitempty,url"\` }`. Nil means unchanged, which is what makes the four fields independently editable per D-08 and lets each onboarding step send only its own field. <threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| authenticated caller -> own record | Authorization, not just authentication, is decided here |
| client -> object storage | An upload bypasses the API and goes straight to the provider |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-01-PRO-01 | Elevation of Privilege | one user reading or editing another's profile | high | mitigate | Target derived only from `SubjectFromContext`; no route exposes an ID parameter and no DTO carries an ID field, asserted by verify gates that grep for their absence plus an ignored-body-ID test |
| T-01-PRO-02 | Information Disclosure | username availability endpoint used to enumerate accounts | high | mitigate | Both username routes sit behind authentication and are limited to 20 requests per minute keyed by the authenticated subject |
| T-01-PRO-03 | Tampering | avatar URL pointed at an attacker-controlled host | medium | mitigate | `avatar_url` carries `binding:"omitempty,url"`; the value the client stores comes from the ticket this API issued, whose public base is the configured bucket |
| T-01-PRO-04 | Denial of Service | oversized or non-image avatar upload | medium | mitigate | Content type restricted to three image types and size capped at 5 MiB, both bound into the presigned request so the provider enforces them |
| T-01-PRO-05 | Tampering | one user overwriting another's stored avatar object | high | mitigate | Object key is scoped by user ID with a random component; a presigned URL is issued only for the caller's own prefix |
| T-01-PRO-06 | Tampering | oversized bio or invalid username reaching storage | medium | mitigate | Validator tags at the boundary plus the matching database check constraints from plan 01-03, with a verify gate asserting the validator pattern and the constraint pattern are identical |
| T-01-PRO-07 | Information Disclosure | profile fields exposing the email to other users | low | accept | `GET /me` returns only the caller's own record in this phase; a friend-visible profile projection arrives with the friend feed in Phase 5 and is that phase's decision |
</threat_model>
