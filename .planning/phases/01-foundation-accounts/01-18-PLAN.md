<contract>
All endpoints under `/v1`. JSON error body `{"error":"<code>"}`. Validation errors from the new endpoints carry fixed strings only, never `err.Error()` of a parse (it can echo the input): `{"error":"validation_failed","field":"password","message":"<fixed text>"}`. The app reads `field`.

Signup token: 32 bytes from crypto/rand, base64url, stored as SHA-256, sent only in header `X-Signup-Token` (never a query string, never a body of a GET). Life: 30 minutes, sliding on each use, never past 6 hours after verification. Unknown, expired and consumed tokens all answer 410 `signup_expired` (410 not 401, because `lib/api/client.ts` refreshes the session on exactly `401 token_expired`). A later Start for the same address does NOT touch an issued token (see Task 4); one live token per address, because a successful Verify replaces the stored token hash.

| # | Endpoint | Auth | Request | Success | Errors |
|---|---|---|---|---|---|
| 1 | POST /auth/signup/start | none | `{email}` (required, email, max 254) | 202 `{sent, retry_after_seconds, code_expires_in}`, identical shape for registered and unregistered addresses | 400 validation_failed (field email); 413 body too large; 429 rate_limited with `retry_after_seconds` and `Retry-After` header |
| 2 | POST /auth/signup/verify | none | `{email, code}` (code exactly 6 digits, otherwise 400 and NOT counted as an attempt) | 200 `{signup_token, expires_in:1800}` | 400 code_incorrect `{attempts_left}`; 410 code_expired; 410 code_attempts_exceeded; 429 rate_limited |
| 3 | POST /auth/signup/birthday | X-Signup-Token | `{birthday:"YYYY-MM-DD"}` | 204, nothing persisted | 400 validation_failed (field birthday); 403 under_minimum_age (pending row deleted); 410 signup_expired |
| 4 | POST /auth/signup/complete | X-Signup-Token | `{password, name, username, birthday, terms_version}`; `password` REQUIRED for an email-kind sign-up and REJECTED for apple or google | 201 AuthResult `{access_token, refresh_token, expires_in, user, is_new_user:true}` with `user.onboarding_complete` true | 400 validation_failed (field one of password, name, username, birthday, terms_version); 403 under_minimum_age; 409 username_taken `{suggestions}` (token stays valid); 409 email_taken; 409 subject_linked; 410 signup_expired |
| 5 | GET /auth/signup/usernames/suggest?name= and /available?username= | X-Signup-Token | query | same bodies as the authenticated `/usernames/*` | 410 signup_expired; 400 validation_failed |
| 6 | POST /auth/oauth/apple and /google | none | unchanged | 200 AuthResult for a known account (as today), OR 200 `{signup_required:true, signup_token, expires_in, email, suggested_name}` for an unknown identity | 400 validation_failed (no email and no stored pending email for that subject); 401 token_invalid; 403 email_not_verified (new: provider says email unverified and no account exists); 409 email_taken (as today) |
| 7 | POST /me/finish-signup | Bearer, behind RequireAuth and RequireVerified | `{birthday, terms_version, name?, username?}` | 200 profile body with `onboarding_complete:true` | 400 validation_failed; 403 under_minimum_age; 409 username_taken `{suggestions}` |

Request bodies on every `/v1` route are capped at 16 KB (413 above that).

Removed: POST /auth/signup, POST /auth/verify-email, POST /auth/verify-email/resend, GET /auth/verify-email/callback (the Safari page). Unchanged: POST /auth/login (request still `min=8,max=72`), /auth/refresh, /auth/logout, GET and PATCH /me, /me/avatar/upload-url, authenticated /usernames/*.

Code rules (from the 01-18 research): 6 digits from crypto/rand, 10 minute life, 5 wrong tries per code, about 15 failures per hour per address (then blocked 1 hour), 60 s resend cooldown, 5 sends an hour and 10 a day per address AND per canonical mailbox (plus tag and Gmail dots removed), every send kills earlier CODES (not earlier tokens), codes stored as HMAC-SHA256 (never plain), constant-time compare, unique index on lower(email) kept.

Birthday is never returned by any endpoint (not in `apiUser`, `profileBody`, `oauthAPIUser`), never shown, never editable, never logged. `user.User` gets NO birthdate field on purpose.

Completeness is redefined: `OnboardingComplete()` = verified email AND name AND username AND non-empty `TermsVersion`.

Terms record while no legal documents exist: `terms_version = 'none'` with `terms_accepted_at` NULL, so the column never claims consent to documents that do not exist. A real version later stores a timestamp.
</contract>

<threat_model>
| Threat | Mitigation |
|---|---|
| Guessing the 6-digit code (1 in a million per try) | 5 tries per code, charged by one atomic UPDATE before compare (20 concurrent guesses charge exactly 5); hourly failure cap of about 15 per address blocks 1 hour and a resend cannot reset it; coarse IP and IP+email limits on top |
| Resend used to get unlimited guesses | Resend replaces the only code hash and resets only the per-code counter; the aggregate counter is untouched |
| Mail bombing an address | 60 s cooldown, 5 an hour, 10 a day per address AND per canonical mailbox (plus tag and Gmail dots stripped), in SQL under row locks (survives API restart); notice emails count against the same caps; IP limits keyed on the IPv6 /64, IP 30 starts an hour |
| Learning whether an address is registered | Same status, body, headers and verify sequence for registered and new addresses (decoy state, decision made inside the locked transaction); owner gets a different email, not a different answer; verify with no row says code_expired. Accepted residual: a caller can learn someone requested a code for an address in the last 10 minutes |
| Code or token stolen from the database | Codes stored as HMAC bound to pending id and email (never plain); token stored as SHA-256; constant-time compare |
| Token leaked through logs or URLs | Header only, never a query; `signup_token` also in the logger's redaction list; request bodies never logged |
| Pre-account takeover (someone registers an address first, owner proves the mailbox later) | /verify never signs anyone in; the unverified legacy row is deleted inside Complete (guarded to rows with no data), the owner chooses a fresh password; email-kind Complete REQUIRES a password, so no verified account can be created that cannot log in; provider claim logic keeps invalidating old passwords and refresh tokens |
| A stranger ending someone's in-progress sign-up | Start never touches an issued token; it dies only by expiry (30 min sliding, 6 h max), Complete or the birthday refusal. Residual: a stranger can still burn code tries (5 per code, 15 an hour) |
| Under 13 account creation | No users row until Complete; server decides age from its own clock at both Birthday and Complete; the pending row is deleted on refusal; the birthday is not kept |
| Birthday disclosure | Column write-only in Go (not a field of `user.User`, never selected), absent from every response, never shown or editable, never logged; test walks every response for any key containing "birth" |
| Validation errors echoing input | Fixed messages only; date errors are sentinels |
| Username check abused before an account exists | Token-scoped limit of 30 a minute plus IP 90; DB unique index stays the decision |
| Limiter map abuse (attacker-chosen keys) | Fixed middleware order (global, IP, then keyed), per-token limiter keyed by pending row id after a valid token lookup, periodic sweep, hard entry cap that fails closed |
| Large bodies on unauthenticated endpoints | 16 KB cap on every `/v1` route, applied before the limiters (413) |
| Late 500 from an invalid username | `ValidateUsername` runs before the insert; 23514 mapped |
| Concurrent starts or completes | Mailbox then pending row lock order on start; compare-and-swap on consume; one transaction on Complete |
| Per-IP limits bypassed with a spoofed X-Forwarded-For | `SetTrustedProxies(nil)` unless `TRUSTED_PROXIES` is set; per-address SQL caps are the real defence |
| Deliberate lockout of someone else's sign-up (15 wrong codes block an address for an hour) | Accepted trade-off of a cap a resend cannot reset |
| Password in memory or on disk on the device | Held in a module variable outside React state, never persisted, cleared on success, Start over and under-13 |
| Log driver prints live codes | Test mode only; documented; startup warning; never use outside local development |
| Destructive tests pointed at the dev database | Both TestMain helpers and the migration test fail unless the database name ends in `_test` |
Honest limits: "We didn't keep your birthday" is true of the database and the device. Nothing is claimed about the mailbox (it already received a code), `api.log` in test mode (address and code), Resend's own logs in production, or the in-memory limiter key for about 10 minutes. The age is self-reported: Start over plus another date works, and the app remembers nothing about a refused attempt by design. An Apple-only or Google-only owner who types their address at sign-up gets a note pointing to the provider button; an email owner who forgot the password has no recovery until Forgot password exists (launch gate).

<decisions_made>
Binding (see top). Resolved while merging the designs and applying the reviews:
- Age check lives on the server; the client always sends the date so the server can delete the pending sign-up.
- Three modes of the same screens: `email`, `provider` (signed out, no account until Create account) and `catchup` (signed in, legacy rows only).
- Catch-up needs no birthday or terms flags on `/me`: every incomplete row has none by definition, so the first step is always Birthday.
- `terms_version` is `none` with a NULL timestamp while no documents exist; the marker for existing accounts is `grandfathered`.
- /start inside the cooldown answers 202 `sent:false`; the Code screen shows a confirmation only for `sent:true`.
- Start never kills an issued token; a new Verify replaces it.
- Email-kind Complete requires a password; social kind rejects one.
- Send caps also count per canonical mailbox.
- Code field uses `maxLength 12` then slices to 6 so a paste is not mangled.
- Countdown is a stored deadline, not a counter.
- No "Verified" interstitial; Code replaces itself with Password so Back never lands on a spent code.
- Start over uses `dismissAll`, not `replace('/welcome')`.
- Code secret derives from JWT_SECRET when `SIGNUP_CODE_SECRET` is unset.
- A provider with an unverified email and no account is refused (403); an Apple repeat without email reuses the stored pending email.
- Usernames before an account: the same handlers on a second route group guarded by the signup token.
- Migration 0004 is not part of this branch; 0003 is applied at cutover, not early.
- The API cutover happens inside Task 15 so the routing hazard can be proven with the new API; the cutover and rollback recipe are written down.
