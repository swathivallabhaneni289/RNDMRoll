Wire the username field and the CTA that Task 1 positioned. Every behavior below is carried over unchanged from the screen this one consolidates: the endpoints, the debounce, and the five states are identical, and only their rendering context changed from a dedicated screen to a row inside a longer form.

**Suggestion.** Call `GET /v1/usernames/suggest?name=` and prefill the field with the returned suggestion. Fire it once on mount when `getDraft().suggestedName` is present, and otherwise on the first blur of the Name field with a non-empty value. The field is never rendered blank, not even for the moment before the suggestion resolves: show it in its `checking` state until the suggestion lands rather than showing an empty box. D-05 states this requirement directly and RESEARCH.md lists the blank field as an anti-pattern. Once a suggestion has been applied, a later Name edit must not overwrite a username the user has since typed.

**The five states**, driven through the `TextField` `status` and `error` props:
- **Idle:** the prefilled suggestion, fully editable. The status row is empty but still occupies its reserved height.
- **Checking:** fires 400 milliseconds after the last keystroke, calls `GET /v1/usernames/available?username=`, and shows the inline spinner with `Checking...` in the status row. UI-SPEC sets this debounce at 400 milliseconds and marks the username field as the only one validated live rather than on blur.
- **Available:** the success-colored check glyph with `Available` in the status row.
- **Taken:** the Copywriting Contract string verbatim, `That username's taken. Try one of these:`, in the status row in the destructive tone, followed by up to three tappable alternate chips from the response. Tapping one fills the field and re-runs the check.
- **Insert-time conflict:** when the live check passed but the save still returns 409, render the same taken state and the refreshed alternates from the 409 response body, not a generic error toast. UI-SPEC calls for exactly that, and RESEARCH.md Pitfall 4 explains why the case is reachable at all, since the availability check and the insert are not one atomic operation.

**Layout contract for the dense rendering.** The status row Task 1 positioned is a fixed-height 24dp region that stays reserved across idle, checking, and available, so the bio field beneath it never shifts as the state changes. The taken state is the one explicit exception UI-SPEC allows: its alternate-chip row renders in a horizontal wrap row directly beneath the status row and may push the bio field and the CTA's scroll-content boundary downward, because real alternates need real estate a fixed-height row cannot pre-reserve. When the state resolves away from taken, that row collapses and the layout returns to the fixed baseline.

Alternate chips use `radius.sm`, `color.secondary` fill, Ink text through `AppText role="label"`, and the flat `subtle` elevation. This is the one place UI-SPEC's Shape table assigns the 4dp chip token on this screen.

Run `ValidateUsername`'s rules client-side too, lowercase letters, digits, and underscores only, 3 to 20 characters, so an obviously invalid entry shows its error without a round trip.

**The single authoritative save.** The CTA is disabled, using the Ink-at-35-percent fill with the Dominant-at-70-percent label and `subtle` elevation that UI-SPEC's CTA fill states paragraph describes, whenever the name is empty or invalid, the username is invalid, or a check is in flight. On press it sends one `PATCH /v1/me` carrying `name` and `username` always, `bio` only when the field is non-empty, and `avatar_url` only when Task 1's upload produced a public URL. Omit rather than null the absent keys, matching the nil-means-unchanged contract the server implements. Then call `reloadUser()`, then `clearDraft()`.

Perform no explicit navigation into the app group. Name and username are set by this point, so `onboarding_complete` becomes true and the root guard from plan 01-05 moves the user into the app group on its own. Keeping that transition with the guard means there is one routing authority rather than two.

## Trust Boundaries

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-01-ONB-07 | Spoofing | username claimed between the availability check and the save | medium | mitigate | The insert-time 409 is a designed state in the UI rather than an error path: the screen re-renders the taken state with fresh alternates, so the race resolves without the user losing the rest of the form they already filled |
| T-01-ONB-08 | Denial of Service | availability endpoint called on every keystroke | medium | mitigate | 400 millisecond debounce on the client, matched by the 20 per minute per-subject server limit from plan 01-11 |
| T-01-ONB-09 | Information Disclosure | photo library access requested more broadly than needed | medium | mitigate | Permissions requested on demand at tap time rather than at screen mount, and a denial leaves the screen fully usable because the photo is optional per D-06 |
| T-01-ONB-10 | Tampering | oversized or non-image upload | medium | mitigate | Content type and size are sent to `POST /me/avatar/upload-url` and bound into the presigned request by plan 01-11, so the storage provider rejects a mismatched upload regardless of client behavior |
| T-01-ONB-11 | Information Disclosure | Apple-supplied name treated as verified identity | low | accept | The prefilled name is untrusted display text, editable by the user before saving, and is never used for authentication or lookup |
| T-01-ONB-12 | Tampering | oversized bio bypassing the client cap | medium | mitigate | The 160 character cap is enforced at the input, at the server validator binding in plan 01-11, and by the database check constraint from plan 01-03 |
