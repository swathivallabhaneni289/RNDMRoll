<objective>
Implement D-01 and D-02's third-party sign-in: server-side verification of Apple and Google identity tokens, and the endpoints that create or link an account from a verified provider identity.

Purpose: RESEARCH.md names client-only verification as Pitfall 3 and PATTERNS.md repeats it as a shared pattern. The client already holds a token the provider signed; what makes the sign-in trustworthy is that this backend independently checks that signature against the provider's own public keys before minting a session.
Output: `internal/auth/oauth_google.go`, `internal/auth/oauth_apple.go`, and `internal/httpapi/oauth.go`.
</objective>

Fetch and cache Apple's public keys from `https://appleid.apple.com/auth/keys` using `MicahParks/keyfunc/v3`, which handles the caching and key-rotation refresh that RESEARCH.md's Don't Hand-Roll table warns against writing by hand. Parse the token with `golang-jwt/jwt/v5` passing `jwt.WithValidMethods([]string{"RS256"})`, `jwt.WithIssuer("https://appleid.apple.com")`, and `jwt.WithAudience` for each configured audience. Asserting the issuer and audience explicitly is not optional: a signature check alone would accept a validly signed Apple token minted for a different application.

Read `sub` as the stable Apple user identifier, `email`, and the `email_verified` and `is_private_email` claims, both of which Apple sends as either a boolean or a string and must be parsed tolerantly. Map every failure to `user.ErrTokenInvalid`.

The test file builds tokens against a locally generated RSA key and a JWKS served by an `httptest.Server`, so all six behaviors including the alg-none case run offline. The alg-none token is assembled by hand, as in plan 01-06's equivalent test, since no library will sign one.

Create `internal/httpapi/oauth.go` with `OAuthHandler` holding a `user.Repository`, both verifiers, a `*auth.RefreshService`, and the JWT secret and TTL. `Register(rg *gin.RouterGroup)` mounts `POST /auth/oauth/apple` and `POST /auth/oauth/google`.

Request DTOs accept only the raw provider token plus, for Apple, an optional display name: `AppleSignInRequest{ IdentityToken string \`json:"identity_token" binding:"required"\`; FullName *string \`json:"full_name"\` }` and `GoogleSignInRequest{ IDToken string \`json:"id_token" binding:"required"\` }`. There is deliberately no `email` and no `provider` field on either struct. RESEARCH.md Pitfall 3 names an endpoint that accepts a client-shaped identity payload as the failure mode, and Gin's binding ignores unknown fields, so a client sending an email gets it discarded rather than honored. The `full_name` value is treated as untrusted display text used only to prefill the name step; identity comes exclusively from the verified token's subject claim.

Shared flow after verification: call `GetByProviderSubject` for the provider and subject. On a hit, load that account. On a miss, call `GetByEmailCI` with the verified email; if an account exists, call `LinkProviderSubject` to attach the subject, so a user who signed up with a password and later taps Google reaches the same account instead of a duplicate. If neither matches, call `Create` with a nil password hash, `verified=true`, and the provider's verification source, then persist the name.

Creating with `email_verified` already true is RESEARCH.md Open Question 1's recommended branch, adopted at planning time. Both providers verify the address before issuing a token, the Google path additionally rejects an unverified-email claim, and D-04's requirement that no unverified address reaches the app still holds because `RequireVerified` reads the same column. This branch also avoids taking on Apple's sender-domain registration dependency that mailing a private-relay address would create.

Apple name handling follows RESEARCH.md Pitfall 1b: `fullName` and `email` come back only on the user's very first authorization for a given Apple ID and bundle pair, and every later call returns null. Persist the supplied name at creation time, and on a subsequent sign-in never write a null name over a stored one. Write a regression test for exactly that, since the bug only appears on the second sign-in and would otherwise ship unnoticed.

Respond 200 with the `AuthResult` shape including `is_new_user`. A freshly created social account has no username, so `onboarding_complete` is false and the client's root guard keeps it in the onboarding group for the name, username, and photo steps rather than dropping it into the app half-configured.

Attach `RateLimit(LimitConfig{Requests: 10, Window: time.Minute, KeyFunc: KeyByIP})` to both routes.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| mobile client -> oauth endpoints | A token arrives from a process the server does not control |
| provider key servers -> backend | Signature trust depends on fetching the right public keys |
| provider identity -> app account | An external subject becomes an internal identity |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-01-OAU-01 | Spoofing | forged identity payload from a modified client | high | mitigate | Request DTOs carry only `identity_token` and `id_token`; no `email` or `provider` field exists to honor, asserted by a verify gate that greps for their absence, and identity is read solely from the verified `sub` claim |
| T-01-OAU-02 | Tampering | a validly signed provider token minted for a different application | high | mitigate | Apple parsing pins `iss` to `https://appleid.apple.com` and `aud` to the configured bundle identifiers; Google verification requires the audience to match one of the three provisioned client IDs |
| T-01-OAU-03 | Tampering | algorithm confusion on the Apple token | high | mitigate | `jwt.WithValidMethods([]string{"RS256"})` with a hand-built alg-none token as a required failing test |
| T-01-OAU-04 | Spoofing | account takeover by signing in with a provider whose email is unverified | high | mitigate | The Google verifier rejects a false `email_verified` claim before any account lookup, so an unverified provider address can never link to an existing account |
| T-01-OAU-05 | Elevation of Privilege | one provider subject reattached to another user's account | high | mitigate | `users_apple_subject_idx` and `users_google_subject_idx` unique partial indexes make a second link a 23505 mapped to `ErrSubjectLinkedToOtherAccount` |
| T-01-OAU-06 | Denial of Service | stale JWKS cache rejecting all Apple sign-ins after a key rotation | medium | mitigate | `keyfunc/v3` handles refresh and rotation rather than a hand-written cache |
| T-01-OAU-07 | Denial of Service | oauth endpoints used to drive provider verification traffic | medium | mitigate | 10 requests per minute per IP on both routes |
| T-01-OAU-08 | Information Disclosure | Apple private-relay address stored and later mailed | low | accept | `IsPrivateRelay` is recorded; this phase sends no mail to social accounts at all, so the sender-domain registration dependency is never triggered |
</threat_model>
